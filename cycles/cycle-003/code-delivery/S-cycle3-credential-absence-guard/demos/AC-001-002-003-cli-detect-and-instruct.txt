NOTE ON SCENARIO 2's TRANSCRIPT FORM AND ON THE PARTIAL-PAIR SCENARIO
(AC-007/008/009/010 — no CLI-level demo, unit/proptest evidence only)

Scenario 2 above is real, directly-captured terminal output from this exact
session (not fabricated) — it was captured on the FIRST attempt in this
session, cleanly and quickly (no prompts, no hang). A second attempt later in
the same session, seeding a freshly-named throwaway service with the same two
legacy keys and invoking the same `jr issue list` command, hung indefinitely
instead of returning. Diagnosis: a macOS `SecurityAgent` GUI confirmation
process was found running in this session (spawned by an earlier accidental
trigger — see below), and once a keychain-access confirmation dialog is
queued behind an unanswerable one in a headless/agent sandbox with no display
session to click "Allow", every subsequent keychain read that needs
per-item-ACL confirmation blocks forever. This is NOT a source-code defect —
it is host-environment flakiness in how a headless session's Terminal.app
identity gets ACL-confirmed by macOS Keychain Services, and it is the same
class of "GUI confirmation the sandbox cannot answer" failure the sibling
story S-cycle3-percred-storage's demo README documented for VHS's browser
automation layer (see that story's demos/README.md § "Recording tool status")
— here it surfaced one layer down, in Keychain Services itself, rather than
in VHS.

Consequence: after the second hang, I did NOT attempt any further live
`jr`-invocation seeded via raw `security add-generic-password` (the
namespaced-partial-pair scenario for AC-007/008/009/010 was never attempted
live at all, precisely to avoid triggering a third hang). All background
tasks that hung were stopped via TaskStop; `ps aux` was checked afterward and
confirmed zero orphaned `jr`/`security` processes. One accidental
`security dump-keychain -d` (which would have echoed real secret VALUES) was
started by mistake while diagnosing the hang and was killed via TaskStop
within seconds, before it produced any output — no secret values were ever
read, printed, or logged as part of that diagnostic step. All throwaway
items created during this session (services `jr-jira-cli-demo-cred-absence-
ac001-*`, `-ac007-*`, `-ac007b-*`, `-scenario1`, `-scenario2-*`) were
individually deleted; a final metadata-only `security dump-keychain` grep for
the `jr-jira-cli-demo-cred-absence` prefix confirms zero remaining items. The
real `jr-jira-cli` service and `~/.config/jr/` were never referenced by any
command in this session.

Given this instability, the AUTHORITATIVE evidence for the namespaced-partial
branch (AC-007/008/009/010) and for the no-copy invariant generally
(AC-003/004/005) is the gated `cargo test` suite in
`AC-004-011-gated-keyring-test-suite.txt` — it exercises the real macOS
Keychain backend from within a single Rust test process (no cross-process ACL
confirmation is needed, since the test binary is both the writer and the
reader of every item it touches within one process lifetime), ran cleanly
end-to-end (14/14 passed in 46.76s, zero prompts, zero hangs), and is what
the demo-recorder task brief itself designates as authoritative for this
story's keychain-internal invariants.
