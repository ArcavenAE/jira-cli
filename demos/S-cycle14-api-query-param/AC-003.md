# AC-003 — Encode-exactly-once, no-trim design default, pinned `--help` text (Behavior 3)

**Traces to:** BC-X.16.001 Behavior 3, Postcondition 3; EC-X.16.001-3/10/11; VP-API-QP-003(e).

## What this demonstrates

NAME and VALUE are each `urlencoding::encode`d EXACTLY ONCE — never `url::form_urlencoded::
byte_serialize` (which would map space to `+` instead of `%20`). Every encoded byte is an RFC
3986 unreserved byte or an uppercase `%HH` triplet. Neither NAME nor VALUE is trimmed of
whitespace (D-380) — an intentional divergence from `-H`/`--header`'s `parse_header`, which DOES
trim.

## Recordings

- `AC-003-special-chars.tape` — `-q 'glob=*' -q 'pct=%' -q 'plus=+' -q 'summary=café'` →
  `glob=%2A&pct=%25&plus=%2B&summary=caf%C3%A9`. `*` → `%2A`, a raw `%` → `%25` (never
  double-decoded), `+` → `%2B` (never left as a literal, form-encoded plus), non-ASCII `é` → UTF-8
  percent-encoded `%C3%A9`.
- `AC-003-no-trim-whitespace.tape` — `-q ' =v' -q 'k= v '`: a whitespace-only NAME (a single
  space) is NOT empty, so it's ALLOWED (not BC-X.16.002's empty-NAME error) and percent-encodes to
  `%20=v` (EC-X.16.001-10); leading/trailing VALUE whitespace is preserved and percent-encoded
  like any other byte, `k= v ` → `k=%20v%20` (EC-X.16.001-11).
- `AC-003-help-text.tape` — `jr api --help | grep -i 'pre-encode'` — pins the literal substring
  "do not pre-encode" (VP-API-QP-003(e)), warning callers that a pre-encoded value (e.g. `%20`)
  would itself be re-encoded (`%20` → `%2520`).

## Result

All three exit 0 with the expected wire strings / help substring visible.

## Verdict

**PASS**.
