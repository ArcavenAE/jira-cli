# AC-005 — `parse_query_param` M1 (no `=` at all); contrast with the allowed empty-VALUE case

**Traces to:** BC-X.16.002 Behavior, EC-X.16.002-1; BC-X.16.001 EC-X.16.001-1/2.

## What this demonstrates

`--query-param foo` (no `=` present at all) is a client-side, pre-HTTP failure: exit 64,
`JrError::UserError`, message `"--query-param must be in NAME=VALUE format (got: {raw})"`. Zero
HTTP calls. Both table and `--output json` modes are demonstrated, with the JSON envelope
(`{"error": "...", "code": 64}`) going to STDERR — the same channel used by every other `jr`
pre-flight error. Contrast: `-q k=` (empty VALUE, non-empty NAME) is explicitly ALLOWED — not an
error at all (EC-X.16.001-1) — so a wire-level demo of that success case is included too.

## Recordings

- `AC-005-m1-error-table-and-json.tape` / `.gif` / `.webm`:
  1. `jr api /rest/x -q novalue; echo "exit=$?"` → `exit=64`, table-mode stderr message.
  2. `jr api /rest/x -q novalue --output json; echo "exit=$?"` → `exit=64`, `{"error":"--query-
     param must be in NAME=VALUE format (got: novalue)","code":64}` on stderr, stdout empty.
  3. `wc -l /tmp/jr-demo-mock-requests.log` → `0` — the mock server's request log (truncated to
     empty by `setup.sh` immediately before this recording) proves BOTH invocations above made
     zero HTTP calls.
- `AC-005-empty-value-allowed.tape` — `jr api /rest/x -q k=` → `query_raw` = `k=`, exit 0. Not an
  error, contrasting directly with the M1 case above.

## Result

Both M1 invocations exit 64 with the pinned message; the mock log stays at 0 lines; `-q k=`
succeeds and is sent as-is.

## Verdict

**PASS**.
