# AC-002 — global `--project` only (issue #862 itself)

**Traces to:** BC-X.7.002 Postcondition 2, EC-X.7.002-2.

## What this demonstrates

This is the exact invocation issue #862 reported as broken: `jr --project FOO user list`, with
the `--project` flag placed **before** the `user list` subcommand (global position), no local
flag, and no configured default. Before this story, `UserCommand::List.project` was a
clap-REQUIRED `String`, so clap's own required-argument check fired before global-value
propagation ever had a chance to fill in the local field — the command failed with exit 2
("the following required arguments were not provided: --project <PROJECT>"), even though a
project key *was* supplied, just in the wrong position for clap's evaluation order.

With the type change to `Option<String>`, clap's `fill_in_global_values` propagation fills the
local field from the global match with no `jr`-level merge code required.

## Recording

Command demonstrated:

```
jr --project FOO user list --no-input
```

Environment: same fake profile as AC-001 (no configured default), no `.jr.toml` ancestor.

## Result

Exit 0. Table output lists two synthetic users with `[project=FOO]` in each display name,
confirming `FOO` was the key actually sent to the mock server (`projectKeys=FOO`) — this exact
command previously exited 2 before this story's `String` -> `Option<String>` change.

## Verdict

**PASS** — the reported #862 bug is fixed; the global-only invocation now resolves and succeeds.
