# AC-009 — `&Config` threaded without reload (non-default `--profile` resolves)

**Traces to:** BC-X.7.002 Fix step 3, Invariants, EC-X.7.002-5.

## What this demonstrates

`cli::user::handle` gained a `&Config` parameter, threaded from `src/main.rs`'s already-loaded
`config` binding (`Config::load_with(cli.profile.as_deref())`) — `handle`/`handle_list` must NOT
call `Config::load`/`Config::load_with` themselves, or `--profile`/`JR_PROFILE` selection would be
silently ignored (the config threaded in would be for the *default* profile, not whichever profile
`--profile` selected). This AC shares its recording with AC-003's sub-cell 2 — see `AC-003.md` for
the full write-up — because it is the SAME observable behavior from two angles: AC-003 asks "does
the configured default resolve"; AC-009 asks "does it resolve for the *correct, non-default*
profile, proving no reload happened." One passing recording demonstrates both: if `handle_list`
reloaded config instead of using the passed `&Config`, `--profile alt` would either be ignored
(falling back to `default`, which has no project — triggering AC-004's exit-64 path instead) or
would silently resolve the wrong profile's state.

## Recording

- `AC-003-AC-009-profile-default.tape` / `.gif` / `.webm` (shared with AC-003; see that file)

Command demonstrated:

```
jr --profile alt user list --no-input
```

## Result

Exit 0, table shows `[project=BAZ]` — the `alt` profile's own configured default, not `default`'s
(which has none, and would have produced AC-004's exit-64 path if the wrong profile's config had
been consulted or config had been reloaded).

## Verdict

**PASS** — `--profile`-selected config is used as-passed, with no reload and no silent fallback
to the default profile.
