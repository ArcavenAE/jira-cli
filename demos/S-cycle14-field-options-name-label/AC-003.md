# AC-003 — `--value` filter matches via the fallback label (EC-X.14.001-13)

**Traces to:** BC-X.14.001 EC-X.14.001-13; BC-X.14.002 (own contract unchanged).

## What this demonstrates

`jr field options --value <substring>` now also matches system-field option names via the
resolved fallback label, as a downstream consequence of AC-001 — **not** a new filter rule.
`filter_options`/`filter_one`'s own matching logic (`BC-X.14.002`) is untouched; it simply now
receives a non-`None` label for rows that used to be `None`.

## Recordings

- `AC-003-value-filter.{tape,gif,webm}`:
  - `jr field options Priority --issue FOO-1 --value high` — matches both `Highest` and `High`
    via their name-derived labels (pre-fix, this would have matched zero rows, since every
    label was `None`).
  - `jr field options Priority --issue FOO-1 --value zzz` — boundary case: no label contains
    the substring, so the command still exits 0 with `"No results found."` — the filter's own
    zero-match behavior is unchanged by this story.

## Result

`--value high` returns 2 rows; `--value zzz` returns 0 rows, exit 0.

## Verdict

**PASS** — the filter matches via the upstream fallback label as a pure downstream effect; its
own matching/exit-code contract is unmodified.
