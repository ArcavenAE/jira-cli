# AC-002 — Presence-based, not emptiness-based (EC-X.14.001-12)

**Traces to:** BC-X.14.001 EC-X.14.001-12.

## What this demonstrates

The fallback checks `Option::is_some()`, never `str::is_empty()`. A wire `"value": ""`
(present-but-empty string) **wins** over a populated `name` — `label: Some(String::new())`,
never falling through merely because the string is empty. A wire `"value": null` deserializes
to `AllowedValue.value: None`, which genuinely IS absent and DOES fall through to `name`.

## Recordings

- `AC-002-presence-semantics.{tape,gif,webm}` — `jr field options "Severity Probe" --issue
  FOO-1`, table and `--output json`. The mock fixture carries both EC-X.14.001-12 cells on one
  field:
  - `{"id": "300", "value": "", "name": "Blank But Named"}` → `label: Some("")` — renders as a
    **blank** Label cell in table mode, `"label": ""` in JSON — never `"Blank But Named"`.
  - `{"id": "301", "value": null, "name": "Falls Through"}` → `value` is truly absent →
    `label: Some("Falls Through")`.

## Result

Both rows are present in the output (never dropped); id 300's label is empty, id 301's label is
`"Falls Through"` — exactly the presence/emptiness distinction this AC pins.

## Verdict

**PASS** — `Some("")` wins over a populated `name`; only a genuine `null`/absent `value`
triggers the fallback.
