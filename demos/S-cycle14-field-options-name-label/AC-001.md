# AC-001 — M1/M2 label-resolution fallback (`value.or(name)`, presence-based)

**Traces to:** BC-X.14.001 Behavior / EC-X.14.001-7..11; `normalize_from_allowed_values_at_depth`.

## What this demonstrates

`src/cli/field.rs::normalize_from_allowed_values_at_depth` now sets
`label = v.value.clone().or_else(|| v.name.clone())` at every depth of the cascading-option
tree. Before this fix it read `label: v.value.clone()` only, so any system-typed field whose
`allowedValues` entries carry only `name` (the real Jira `priority` shape — `{id, name,
iconUrl}`, no `value` key) rendered every row as `"(unnamed)"` (table) / `null` (JSON).

## Recordings

- `AC-001-priority-name-fallback.{tape,gif,webm}` — `jr field options Priority --issue FOO-1`
  (M1 editmeta path) in both table and `--output json` mode. The mock's `priority` fixture
  ships `allowedValues` shaped exactly like real Jira (`{id, name, iconUrl}`, no `value`). Table
  shows `Highest`/`High`/`Medium`; JSON shows `"label": "Highest"`, never `null`.
- `AC-001-m2-createmeta.{tape,gif,webm}` — the same fallback exercised via the M2 (`--type`)
  path against a different system field, `Components` (`{id, name}` allowedValues, no
  `value`). Success shows `Backend`/`Frontend`. The tape's second command is an **error path**
  demonstrating the M2 project-resolution error taxonomy is pre-existing and untouched: an
  unresolvable `--project BADPROJ` still exits 64 with the same message as before this fix.
- `AC-001-cascading-and-custom-value.{tape,gif,webm}` — EC-X.14.001-11: a cascading custom
  field (`Category`) whose one child carries only `name` (`Storage Only`) — the fallback
  recurses into cascading children, not just the top level. The second command
  (`Environment`, an ordinary custom select whose entries already carry `value`) is a
  cross-reference showing custom-field labels are byte-for-byte **unaffected**.
- `AC-001-neither-present-unnamed.{tape,gif,webm}` — EC-X.14.001-7/EC-X.14.001-10: an entry
  carrying **neither** `value` nor `name` (`Legacy Probe`, `{"id": "99"}`) still renders as a
  row (never dropped) with `label` degrading to `"(unnamed)"` (table) / `null` (JSON) — the
  same degenerate-entry rendering contract AC-005 cross-references (BC-X.14.003, unchanged).

## Result

Every case exits 0 (or 64 for the two pre-existing, unaffected error paths); system-field
labels now resolve via `name` exactly like custom fields already did via `value`.

## Verdict

**PASS** — the presence-based `value.or(name)` fallback behaves per EC-X.14.001-7..11 across
the M1 and M2 enumeration mechanisms, at both the top level and a cascading-child level, without
disturbing custom-field labels, the degenerate "neither present" case, or M2's own,
pre-existing error taxonomy.
