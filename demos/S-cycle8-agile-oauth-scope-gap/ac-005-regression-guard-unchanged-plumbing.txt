=== AC-005: resolve_oauth_scopes / build_authorize_url are UNCHANGED — regression guard ===

Test: src/cli/auth/tests/mod.rs::resolve_oauth_scopes_inspects_passed_profile_not_active

What this proves:
  This story is a pure constant-literal expansion (8 -> 16 scopes) in
  src/api/auth.rs::DEFAULT_OAUTH_SCOPES. AC-005 requires that the
  downstream plumbing which reads this constant and builds the OAuth
  authorize URL — src/cli/auth/login.rs::resolve_oauth_scopes and
  src/api/auth.rs::build_authorize_url — is UNCHANGED by this story. Both
  functions already emit the full scope-union string with `prompt=consent`
  hardcoded, which already satisfies Atlassian's "always request the full
  intended union on every new consent" requirement regardless of how many
  scopes are in the set.

  This test is a regression guard, not a new-behavior test: it asserts
  resolve_oauth_scopes reads the *passed* profile (not the active one) when
  a profile has a custom oauth_scopes override — proving the resolution
  function's contract is untouched and still correctly profile-scoped after
  the DEFAULT_OAUTH_SCOPES literal grew. If this story had accidentally
  touched resolve_oauth_scopes's profile-selection logic while editing the
  adjacent constant, this test would catch it.

  The zero-diff claim itself (no lines changed in login.rs or
  build_authorize_url) is confirmed directly against the source tree below,
  not just inferred from this test passing.
