# S-639-1 — Pre-flight Exit-64 Guards for `--field` and `--on-behalf-of` on Platform Create Path

## Narrative

As a `jr issue create` caller who supplies `--field` or `--on-behalf-of` without
`--request-type` on the platform path, I want an immediate, actionable exit-64 error
that tells me these flags are JSM-only and how to use them correctly, so that I
do not waste time waiting for a server-side error from a platform POST that was
destined to fail or silently ignore my flags.

*Breaking change: callers who previously relied on the warn-and-proceed behavior
(exit 0 + issue created despite the stray flag) must either add `--request-type` or
remove the flag. Ships v0.6.0-dev.12. See CHANGELOG.md `### Breaking Changes`.*

## Problem Statement

After PR #381 (issue #288 dispatch fork), `--field` and `--on-behalf-of` are accepted as
CLI flags on `jr issue create` but WARN and then proceed on the platform path (exit 0,
issue created, flags silently dropped). This is misleading: the flags are self-declared
JSM-only flags whose names signal their purpose. A caller who supplies them without
`--request-type` has made a categorical error — not an ambiguous choice. DEC-188 promotes
these guards from `eprintln!` warn-and-proceed (S-383) to `JrError::UserError` exit-64
pre-flight, matching the mutual-exclusion guard pattern in `src/cli/issue/edit.rs::handle_edit`.

**Asymmetry invariant:** `--field`/`--on-behalf-of` → exit 64 (self-declared JSM-only flags).
`--team`/`--points` → warn-only (BC-3.8.011; general platform flags the JSM API happens not
to support; flag choice is ambiguous). Do NOT apply this story's pattern to the warn-only group.

## Guard Implementation Pattern

Model the guard on `src/cli/issue/edit.rs::handle_edit` mutual-exclusion block
(lines ~167–222). Guard placement: AFTER the JSM dispatch fork at `create.rs` ~:49
(`if request_type.is_some() { return handle_jsm_create(...) }`), BEFORE project-key
resolution, BEFORE interactive prompts, BEFORE all pre-POST helper HTTP, and BEFORE
the platform POST. Combined-flag check fires FIRST (both `!field_pairs.is_empty()` AND
`on_behalf_of.is_some()`), producing ONE combined error. Single-flag checks follow for
each independently. ONE error per invocation regardless of how many `--field` values
are passed (`!field_pairs.is_empty()` is presence-only).

**MUST NOT** use `#[arg(requires = "request_type")]` — that yields clap exit 2, not
exit 64 `JrError::UserError`, violating BC-3.8.012/013 (falsified by AC-1/AC-2/AC-16).
