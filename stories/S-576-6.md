## Acceptance Criteria

### AC-001 (traces to BC-2.7.001/002/007, BC-3.9.001/008/009/010: platform ES attachment round-trip)

`test_e2e_attachment_platform_roundtrip` in `tests/e2e_live.rs` — gated `JR_RUN_E2E=1` + `#[ignore]` + `if !e2e_enabled() { return; }`.

**Steps:**
1. Create a fresh ES issue via `e2e_harness()` (`let h = e2e_harness()`). Use `run_label()` to get the sweep label (`let rl = run_label()`); build a summary `let summary = format!("[e2e {}] attachment round-trip", rl)`; create the issue via `seed_issue(&h, &rl, &summary)` (3-arg form per `tests/e2e_live.rs`; `--label <rl>` is applied internally from the label arg). Capture `key`. These ensure the CI sweeper (e2e.yml `if: always()` teardown, JQL `labels=e2e-$GITHUB_RUN_ID`) can pick up the issue if the test fails before step 9.

### AC-010 (teardown obligations — structural property)

No separate test function. Teardown is built into each test (AC-001 through AC-004). This AC documents the obligations and verifies they are fulfilled.

**Teardown mechanism constraint:** `assert!` / `assert_eq!` panics unwind the stack and skip any cleanup code that follows. Therefore teardown MUST NOT rely on sequential post-assert cleanup. Two acceptable mechanisms:

- **Drop-guard pattern (mandatory for AC-002; strongly preferred for AC-001/003/004):** Wrap the captured AID (and EJ key) in a struct whose `Drop` impl runs the delete/close commands. The guard runs on normal return AND on unwind, ensuring cleanup even when an assertion panics.
- **Collect-results-then-assert (acceptable alternative for AC-001):** Run all steps, store results in variables; perform all assertions after teardown completes. This avoids mid-test panics but requires care to not mask earlier errors.

**ES platform test (AC-001):**
- The uploaded attachment AID MUST be deleted in-test via `jr issue attachment delete <aid> --yes --output json` (step 7) before any assertion failure. Use Drop-guard or collect-results-then-assert to guarantee deletion even if a mid-test assertion panics.
- Pattern: capture `aid` immediately at upload; register it in the Drop-guard before any further assertions.

**EJ JSM tests (AC-002, AC-003, AC-004):**
- **AC-002 specifically MUST use the Drop-guard pattern** (public attachment persists independently of ticket status per ADV-022; a panic between upload and teardown leaves a permanent customer-visible residue). The Drop-guard MUST: (1) delete the AID via `jr issue attachment delete <aid> --yes`; (2) call `jsm_self_close(key, &h)`. Ordering: AID delete BEFORE jsm_self_close.
- AC-003 and AC-004 SHOULD use Drop-guard; collect-results-then-assert is acceptable if Drop-guard is impractical.
- Best-effort: if AID deletion or jsm_self_close fails inside Drop, emit `eprintln!("[WARN] …")` and continue; NEVER propagate panics from Drop.

**Residual orphan risk:** Accepted LOW (per `docs/specs/jsm-e2e-coverage.md §6.3`). If Drop itself panics (e.g., double-panic during unwind), cleanup is skipped — this is an inherent Rust limitation. EJ issues do not affect the ES project or CI.
