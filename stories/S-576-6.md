## Narrative

- **As a** jr maintainer
- **I want** comprehensive live-Jira E2E tests that exercise all `jr issue attachment` subcommands against a real Jira Cloud instance
- **So that** wire-shape regressions in the attachment surface are caught before they reach production — the same rigour applied to other write commands in the JSM E2E expansion (S-JSM-E2E-1 precedent)

As a fork contributor, I want all JSM attachment tests to clean-skip loudly when `JR_E2E_JSM_PROJECT` is unset, so that my CI runs are never red because of missing JSM project configuration.

## Acceptance Criteria

### AC-001 (traces to BC-2.7.001/002/007, BC-3.9.001/008/009/010: platform ES attachment round-trip)

`test_e2e_attachment_platform_roundtrip` in `tests/e2e_live.rs` — gated `JR_RUN_E2E=1` + `#[ignore]` + `if !e2e_enabled() { return; }`.

**Steps:**
1. Create a fresh ES issue (reuse `e2e_cmd()` harness with `JR_E2E_PROJECT`); capture `key`.
2. Create a small in-memory test file (e.g., `"attachment-e2e-test-<run_id>.txt"` with ASCII-printable content `"jr e2e attachment round-trip <run_id>"`). Filename MUST be platform-neutral: ASCII-only, no Windows-reserved names (CON, NUL, COM1, etc.), no control characters. Write to a `tempfile::TempDir`.
3. **Upload**: `jr issue attachment upload <key> <file_path> --output json --yes`. Assert exit 0. Parse JSON array; assert it is non-empty. Capture `aid = arr[0]["id"]` (as string). Assert `aid` is non-empty.
4. **List (table)**: `jr issue attachment list <key>`. Assert exit 0. Assert stdout contains the filename (BC-2.7.001).
5. **List (JSON)**: `jr issue attachment list <key> --output json`. Assert exit 0. Parse JSON array. Locate the item with matching `id == aid`. Assert item has `"filename"`, `"contentUrl"`, `"mimeType"`, `"size"`, `"created"`, `"author"` keys (BC-2.7.002). `contentUrl` MUST be non-null non-empty string.
6. **Download**: `jr issue attachment download <key> <aid> --out <tempdir/downloaded.txt>`. Assert exit 0. Assert the output file exists (BC-2.7.007). Assert file content is not empty.
7. **Delete**: `jr issue attachment delete <aid> --yes --output json`. Assert exit 0. Assert JSON is `{"deleted":true,"id":"<aid>"}` (BC-3.9.010).
8. **List post-delete**: `jr issue attachment list <key> --output json`. Assert exit 0. Parse array. Assert no item has `id == aid` (BC-3.9.008 — AID removed).
9. **Issue teardown**: Transition the ES issue to done via `jr issue move <key> $JR_E2E_STATUS_DONE` (best-effort; warn on failure; do NOT fail the test on close failure). Or leave open — ES issues are caught by the label-based CI sweeper.

**Post-condition assertions (equivalent to wiremock `.expect`):** Steps 7–8 together verify deletion: delete command exits 0 AND the subsequent list confirms the attachment is gone. This two-step pattern substitutes for mock request-count assertions in live E2E context.

**Note on step 2 filename:** U+007F (DEL) is NOT portable across CI environments; never use it in test filenames or file content. Windows CI runner restrictions apply (B4/B5, S-576-2): keep filenames within ASCII-printable range, no Windows path separators, no reserved device names. File extension `.txt` is safe on all platforms.

- **Test:** `tests/e2e_live.rs::test_e2e_attachment_platform_roundtrip`

### AC-002 (traces to BC-3.9.003/007/011: JSM EJ --public echo shape with P2-3c schema pinning)

### AC-010 (teardown obligations — structural property)

No separate test function. Teardown is built into each test (AC-001 through AC-004). This AC documents the obligations and verifies they are fulfilled.

**ES platform test (AC-001):**
- The uploaded attachment AID MUST be deleted in-test via `jr issue attachment delete <aid> --yes --output json` (step 7) before the test ends or before any assertion failure. If the upload step succeeds but a subsequent step fails (e.g., download), the test MUST still attempt AID deletion as cleanup.
- Pattern: capture `aid` immediately at upload; on any early-return path after upload, delete the AID (best-effort; warn on failure).

**EJ JSM tests (AC-002, AC-003, AC-004):**
- The uploaded attachment AID MUST be deleted via `jr issue attachment delete <aid> --yes` BEFORE calling `jsm_self_close(key, &h)` (BC-3.9.011 ADV-022 obligation: `jsm_self_close` closes the ticket but the attachment file persists as customer-visible residue independently of ticket status; the attachment AID is permanent until explicitly deleted).
- `jsm_self_close(key, &h)` MUST be called for every EJ issue key captured, on ALL exit paths including early-return paths (use `defer`-style cleanup: capture key early, always-close at end or on any failure path).
- Best-effort: if AID deletion or jsm_self_close fails, emit `eprintln!("[WARN] …")` and continue; NEVER fail the test on teardown failure.

**Residual orphan risk:** Accepted LOW (per `docs/specs/jsm-e2e-coverage.md §6.3`). If a test panics between `create` and `jsm_self_close`, the EJ issue stays open. EJ issues do not affect the ES project or CI.
