## Narrative

- **As a** developer or team lead using `jr` to inspect Jira issues
- **I want** `jr issue attachment list <KEY>` to display all attachments as a table and optionally as JSON, with client-side filtering by MIME type, filename, and size
- **So that** I can discover, audit, and select specific attachments on a Jira issue without opening the web UI, and downstream scripts can parse attachment metadata reliably (including the `contentUrl` field from issue #585)

## Acceptance Criteria

### AC-001 (traces to BC-2.7.001 postcondition: table columns in display order)

`jr issue attachment list <KEY>` against a wiremock-served issue with one attachment renders a comfy-table on stdout with exactly six columns in order: **ID | Filename | Type | Size | Created | Author**. The `Size` column shows human-readable formatted bytes (e.g., `42.0 KB`). The `Author` column shows `displayName`; falls back to `accountId` when `displayName` is absent/null; falls back to `"(anonymous)"` when both are absent/null (full chain per EC-2.7.001-3). Thumbnail field is NOT present in the table.

**Display-sanitization mandate (SEC-576-011, CWE-116)**: the `display_sanitize_filename` helper (see Architecture Compliance Rules) is called on EVERY `filename` value before rendering in the Filename column. `display_sanitize_filename` replaces ALL ASCII control characters in the byte range 0x00–0x1F and 0x7F with `?` (CWE-116 terminal injection prevention — BC-2.7.011 display-sanitization clause). This is the ONLY operation it performs: it does NOT strip path separators, does NOT truncate to 214 bytes, and does NOT filter Windows device names (those belong to `sanitize_attachment_filename` in S-576-2, which is the disk-path variant). A filename containing null bytes or control characters MUST render as the sanitized form, never the raw form, in the table. The helper lives in `src/cli/issue/attachments.rs` and is the canonical first instantiation.

- **Test:** `tests/attachment_list.rs::test_bc_2_7_001_table_six_columns_order` (wiremock)

---

### AC-002 (traces to BC-2.7.001 postcondition: zero-attachment empty table)

When the issue exists but has zero attachments, `jr issue attachment list <KEY>` exits 0 with empty stdout (pipe-friendly) and emits `"No attachments on <KEY>."` to stderr. In JSON mode (`--output json`), exit 0, stdout `[]`, no stderr.

- **Test:** `tests/attachment_list.rs::test_bc_2_7_001_zero_attachments_empty_stdout_stderr_hint`

---

### AC-003 (traces to BC-2.7.002 postcondition: JSON array shape; contentUrl rename; #526 invariant)

`jr issue attachment list <KEY> --output json` returns a pretty-printed JSON array routed through `output::render_json` (#526 invariant — NOT `serde_json::to_string_pretty`). Each element has exactly the keys `{author, contentUrl, created, filename, id, mimeType, size}` in BTreeMap-alphabetical order. Key invariants:
- `"self"` MUST be OMITTED from every element (VP-576-004 assertion 1).
- `"content"` MUST be RENAMED to `"contentUrl"` in every element (VP-576-004 assertion 2).
- `size` is a raw `u64` integer (bytes), not a human-formatted string.
- `author` is `null` when the author field is absent or null in the Jira API response.

**VP-576-004 list half**: assert no element contains `"self"` key AND every element contains `"contentUrl"` and no element contains `"content"` key.

- **Tests:** `tests/attachment_list.rs::test_bc_2_7_002_json_shape_curated_form` (VP-576-004 list half); `tests/attachment_list.rs::test_bc_2_7_002_json_uses_render_json_not_string_pretty`

### AC-004 (traces to BC-2.7.001 postcondition: filter-count hint; BC-2.7.002: JSON hint behavior)

When a `--filter` flag is active and reduces the displayed row count (N < M), a hint is emitted to stderr: `"Showing N of M attachments."` This hint fires in BOTH human and JSON modes (BC-2.7.001 EC-2.7.001-2). When a filter is active but excludes nothing (N == M), the hint is NOT emitted. When no filter is active, no hint is emitted.

- **Test:** `tests/attachment_list.rs::test_bc_2_7_001_filter_count_hint_fires_when_reduced`

---

### AC-005 (traces to BC-2.7.003 postcondition: mime glob filter)

`--filter mime=<glob>` retains only rows whose `mimeType` matches the glob (case-insensitive; `*` matches any sequence including `/`). Full attachment list is fetched before filtering. Combined with `--output json`, returns only matching elements.

- **Test:** `tests/attachment_list.rs::test_bc_2_7_003_mime_filter_image_wildcard`

---

### AC-006 (traces to BC-2.7.004 postcondition: name glob filter; AND composition)

`--filter name=<glob>` retains only rows whose `filename` matches the glob (case-insensitive). Multiple `--filter` flags combine with AND semantics. JRACLOUD-96384 note: multiple attachments sharing the same `filename` are all returned; no dedup.

- **Test:** `tests/attachment_list.rs::test_bc_2_7_004_name_filter_glob_and_composition`

---

### AC-007 (traces to BC-2.7.005 postcondition: size-max filter)

`--filter size-max=<bytes>` retains only rows whose `size` (bytes, u64) ≤ the given limit. A non-integer argument → exit 64 before any HTTP call. `--filter size-max=0` retains zero-byte attachments only.

- **Test:** `tests/attachment_list.rs::test_bc_2_7_005_size_max_filter_and_parse_error`

---

### AC-008 (traces to BC-2.7.003 EC-2.7.003-2: invalid filter key or missing =)

If a `--filter` value does not contain `=` → exit 64, message includes `"Invalid filter '<VALUE>': expected key=value form. Accepted keys: mime=, name=, size-max=."`. If the key before `=` is unknown → exit 64, message includes `"Unknown filter key '<KEY>'. Accepted keys: mime=, name=, size-max=."`. Both cases fire before any HTTP call.

- **Test:** `tests/attachment_list.rs::test_bc_2_7_003_invalid_filter_key_exits_64`

### Task 3: Implement `display_sanitize_filename` (pure helper — CWE-116; SEC-576-011)

**CRITICAL — CWE-116 display-sanitization ONLY (P1-005)**: `display_sanitize_filename(name: &str) -> String` replaces ALL ASCII control characters in the byte range 0x00–0x1F and 0x7F with `?`. That is the COMPLETE algorithm. It does NOT:
- Strip path separators (`/`, `\`, `:`) — those are disk-path concerns for `sanitize_attachment_filename` in S2
- Truncate to 214 bytes — no truncation
- Filter Windows device names (CON, NUL, COM1, etc.) — disk-path concern
- Strip leading dots — disk-path concern
- Apply step 5.5 trailing whitespace/dot strip — disk-path concern

The function always returns a `String` (never `None`/`Option`). If the input is all control chars, the result is a string of `?` characters — still returned.

Write unit tests in `src/cli/issue/attachments.rs #[cfg(test)]` covering: null byte (`\0`), DEL (`\x7F`), tab (`\t`), newline (`\n`), `\x1F`, and a normal filename (unchanged). All pure-core, no wiremock needed.

**Distinction**: `display_sanitize_filename` (this helper, S1) is the display-channel variant — prevents terminal injection. `sanitize_attachment_filename` (S2) is the disk-path variant — implements the full BC-2.7.011 5-step CWE-22 algorithm with path-separator stripping, device-name filtering, 214-byte cap, and containment check. They are separate functions; neither calls the other. Do NOT conflate them.
