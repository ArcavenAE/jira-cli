## Narrative

- **As a** developer managing JSM Jira comments from the CLI
- **I want** `jr issue comment edit KEY --id ID [--internal | --public [--yes]]` to change
  a comment's visibility atomically with its body update
- **So that** I can make internal agent notes truly internal and make restricted comments
  public, with safety confirmation for the --public direction that can be bypassed
  non-interactively with --yes

### Visibility Flag Branching in handle_comment_edit

Extends the pipeline from S-577-4 at step 5 (after body source resolution, empty guard, ADF):

```
After step (3) empty guard:
  if internal && public → unreachable (clap conflicts_with)
  
(4.5) Confirmation gate (only when --public):
      non-interactive without --yes → exit 64 + "Use --yes to confirm" hint
      --stdin detected (via no_input flag since --stdin was passed) → exit 64 +
        "--stdin disables interactive prompts. Use --yes to confirm."
      interactive y/N → dialoguer::Confirm::interact_on(&Term::stderr())
        Err(_) → JrError::Interrupted (exit 130)
        Ok(false) → return cancelled envelope
      --yes → skip prompt

(4.6) JSDCLOUD-6050 hint:
      --internal → eprintln!("note: JSDCLOUD-6050: …") BEFORE HTTP PUT
      --public → eprintln!("note: JSDCLOUD-6050: …") AFTER confirmation, BEFORE PUT

(5) HTTP PUT: client.update_comment(key, id, adf_body, internal_flag, public_flag)
    --internal → internal_flag = Some(true), public_flag = None
    --public   → internal_flag = None,       public_flag = Some(true)
    neither    → both None (body-only, handled in S-577-4)

(6) Build response JSON:
    changed_fields.body = raw pre-trim body (same as S-577-4)
    changed_fields.jsm_internal = true  when --internal
    changed_fields.jsm_internal = false when --public
    (absent when neither — S-577-4's responsibility)
```

### Cancelled Envelope (--public interactive cancel)

When the user answers N to the `--public` confirmation:

```json
{
  "cancelled": true,
  "updated": false
}
```

Key set: exactly `["cancelled", "updated"]`. No `"id"` or `"key"` keys (not confirmed
server-side). `"updated"` is JSON boolean `false` — VP-577-029 exact pin. NOT a timestamp
or empty string. The key MUST be present for BTreeSet assertion consistency.

### JSDCLOUD-6050 Hint Text

```
note: JSDCLOUD-6050: Jira's properties PUT uses MERGE semantics — existing
properties not included in the request are PRESERVED. A body-only PUT (no
--internal/--public) does not change visibility. To make a comment internal,
use --internal; to make it public, use --public.
```

The exact text may vary, but `"JSDCLOUD-6050"` MUST appear in the stderr output (VP-577-010
and VP-577-017 key substring check). This hint fires even with `--output json` (it goes
to stderr, not stdout).

### BC-3.5.006 Delivery Obligation (a): CLAUDE.md MERGE Verdict

Add to CLAUDE.md under `## Gotchas` (or `## Key Decisions`):

```
- **`jr issue comment edit --internal/--public` uses MERGE semantics on Jira's properties
  endpoint (BC-3.5.006, JSDCLOUD-6050):** A PUT to `/rest/api/3/issue/{key}/comment/{id}`
  with a `properties` array MERGES with existing properties — it does NOT replace them.
  A body-only PUT (no `--internal`/`--public`) leaves visibility UNCHANGED (PRESERVED
  semantics). Confirmed by `.factory/research/issue-577-comment-crud-jsdpublic-2026-07-09.md`.
  Do NOT attempt to clear visibility by omitting properties; use `--public` explicitly.
```

This CLAUDE.md entry is a mandatory delivery obligation for this story's PR.

The three scenarios are (BC-3.5.006 obligation b, spec v1.3.40):

**Scenario 1 (5-step MERGE probe):**
(1) Create JSM comment via `jr api POST` with `sd.public.comment={internal:true}`.
(2) GET; assert internal=true. (3) `jr issue comment edit KEY --id CID "body" --internal`.
(4) GET; assert internal=true (MERGE preserved). (5) Second `--internal` PUT; GET; assert stable.

**Scenario 2 (PRESERVED base — 2-step):**
(1) Create JSM comment via `jr api POST` WITH a role/group visibility restriction.
(2) `jr issue comment edit KEY --id CID "body-only"` (no `--internal`/`--public`).
(3) GET; assert restriction SURVIVES (confirms PRESERVED verdict from
`.factory/research/issue-577-visibility-put-semantics-2026-07-09.md`).

**Scenario 3 (compound cell — ADDITION to Scenario 2, NOT a substitute):**
(1) Create JSM comment via `jr api POST` carrying BOTH a role/group restriction AND
a `jr.test.marker` property.
(2) PUT body = `{"body": <adf>, "properties": [{"key": "sd.public.comment", "value": {"internal": false}}]}`
with NO `visibility` key.
(3) GET; assert BOTH the restriction AND `jr.test.marker` SURVIVE.
Closes the weakest safety-table cell: MERGE for properties does not interfere with
PRESERVED for visibility when both are simultaneously present.
Scenario 3 is an explicit ADDITION to Scenario 2 — both MUST run.

#[tokio::test]
#[ignore]
async fn test_e2e_comment_edit_visibility_merge_semantics() {
    if !e2e_enabled() { return; }
    let jsm_project = match std::env::var("JR_E2E_JSM_PROJECT").ok() {
        Some(p) if !p.is_empty() => p,
        _ => return, // clean skip when JSM project not configured

    // (2) GET; assert comment is internal (internal=true)

    // (4) GET; assert comment is still internal (MERGE: existing sd.public.comment PRESERVED)
    // (5) jr issue comment edit KEY --id CID "body again" --internal (second identical PUT)
    //     GET; assert internal=true still (MERGE is stable on repeated --internal)
    // Teardown: jr issue comment delete KEY --id CID --yes

    // (1) Create probe comment via jr api POST carrying a role/group visibility restriction
    // (2) jr issue comment edit KEY --id CID "body-only edit" (no --internal/--public)

## Architecture Compliance Rules

(Extracted from CLAUDE.md, BC-3.5.006/007/008, DEC-169)

1. **`interact_on(&Term::stderr())` is unconditional (all builds).** Same constraint as
   S-577-3. The `--public` confirmation prompt uses `dialoguer::Confirm` with
   `interact_on(&Term::stderr())`. Not gated by any cfg attribute.

2. **`dialoguer::Error` → `JrError::Interrupted` (exit 130).** EC-3.5.008-5. Must not be
   swallowed or mapped to the cancel path.

3. **--yes MUST NOT have `requires("public")` in clap.** EC-3.5.008-4, DEC-169. The
   `--yes` flag is a general confirmation bypass accepted silently on non-public paths.
   If clap `requires("public")` is present, `--yes` without `--public` will clap-exit 2,
   breaking the silent no-op contract. Tested by AC-010.

4. **JSDCLOUD-6050 hint goes to stderr, not stdout.** Even with `--output json`, the hint
   is `eprintln!()` to stderr. It must NOT appear in the stdout JSON envelope.

5. **MERGE semantics are documented in CLAUDE.md.** BC-3.5.006 delivery obligation (a) is
   not optional. The CLAUDE.md entry ships in the SAME PR as the implementation. This is a
   correctness-critical gotcha (a body-only PUT PRESERVES visibility — the wrong mental
   model leads to unintentional visibility changes).

6. **E2E test is gated.** The `test_e2e_comment_edit_visibility_merge_semantics` function
   MUST have `#[ignore]` + `if !e2e_enabled() { return; }` early-return per the two-layer
   gate pattern. Clean-skip when `JR_E2E_JSM_PROJECT` is unset.

7. **Cancelled envelope key set is exact.** `{"cancelled":true,"updated":false}` has exactly
   2 keys. `"id"` and `"key"` MUST NOT appear (not confirmed server-side on cancel).
   `"updated"` is boolean `false` (VP-577-029 exact pin — NOT a timestamp or empty string).
