### Wire Shape Details

`delete_comment`: `DELETE /rest/api/3/issue/{encoded_key}/comment/{id}` → 204 OK.

`update_comment` with `visibility_flag: None` (body-only):
```json
{ "body": { "version": 1, "type": "doc", "content": [...] } }
```

`update_comment` with `visibility_flag: Some(true)` (--internal):
```json
{
  "body": { ... },
  "properties": [{ "key": "sd.public.comment", "value": { "internal": true } }]
}
```

`update_comment` with `visibility_flag: Some(false)` (--public):
```json
{
  "body": { ... },
  "properties": [{ "key": "sd.public.comment", "value": { "internal": false } }]
}
```

`get_comment`: `GET /rest/api/3/issue/{encoded_key}/comment/{id}?expand=properties`

### Implementation Pattern (mirrors add_comment)

`add_comment` already uses `urlencoding::encode(key)` and `serde_json::json!` macro
payload construction. All three new methods MUST use the same patterns:
- `urlencoding::encode(key)` in the path format string
- `serde_json::json!` for the PUT body (option (d) in BC-3.5.005 implementation note:
  `"properties"` conditionally injected via `if let Some(internal) = visibility_flag { ... }`)
- Return `serde_json::Value` (NOT the typed `Comment` struct) from update_comment and
  get_comment — the typed struct silently drops `"self"`, `"updateAuthor"`, `"jsdPublic"`

### Forbidden Dependencies

`src/api/jira/issues.rs` MUST NOT gain any new crate-level imports for these methods.
`urlencoding` and `serde_json` are already in scope. No new `use` statements needed.

```rust
pub async fn update_comment(
    &self,
    key: &str,
    id: &str,
    body: Value,
    visibility_flag: Option<bool>,
) -> Result<()> {
    let path = format!(
        "/rest/api/3/issue/{}/comment/{}",
        urlencoding::encode(key),
        id
    );
    let mut payload = serde_json::json!({ "body": body });
    if let Some(internal) = visibility_flag {
        payload["properties"] = serde_json::json!([{
            "key": "sd.public.comment",
            "value": { "internal": internal }
        }]);
    }
    self.put(&path, &payload).await
}
```

## Architecture Compliance Rules

(Extracted from `src/api/jira/issues.rs`, CLAUDE.md, BC-3.5.005 implementation note)

1. **`urlencoding::encode(key)` in every path.** All three methods encode the key path
   segment. This is non-optional (EC-3.5.002-2); existing `add_comment` already does this.

2. **`serde_json::json!` macro for PUT body.** Option (d) from BC-3.5.005 implementation
   note: use `json!` with conditional `properties` injection. Do NOT use a separate PUT
   request struct (avoid the hazard of omitting `skip_serializing_if` on non-body fields).

3. **`update_comment` returns `Result<()>`.** `JiraClient::put` discards the response body
   (returns `Result<()>`). Handlers in S-577-4/5 construct the success JSON from local
   state (CLI args + raw input + literal `"updated": true`), not from the Jira response body.
   This is correct: `updated` is a literal boolean `true` per spec (BC-3.5.005), not a
   timestamp from the API. `get_comment` (a separate method) returns `Result<Value>` for
   its passthrough requirement.

4. **`get_comment` returns `serde_json::Value`, NOT `Comment`.** Same reason as above.
   The response passthrough is mandatory (BC-3.5.010: "No typed Comment round-trip").

5. **No new Cargo.toml dependencies.** `urlencoding = "2"` and `serde_json` are already
   in scope. Do NOT add new crate imports.

6. **LOC guard.** issues.rs is currently ~841 LOC. Adding ~60-70 LOC for three methods
   remains under the ADR-0012 1,000-LOC threshold. If the actual addition pushes it past
   900 LOC, note the risk in the PR but do NOT extract in this story.
