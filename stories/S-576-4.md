> **SETTLED RULINGS — encode these exactly, do not re-litigate:**
> - **DEC-168 (404 on targeted delete = exit 64 + surface body)**: When `jr issue attachment delete <AID>` targets a specific AID and receives 404, exit 64 + stderr MUST BEGIN with the canonical prefix `"Attachment <AID> not found or not accessible."` followed by the Jira error body as detail (EC-3.9.008-2 ~3469). The prefix comes first, then the body — NOT body-only. This is NOT a silent exit 0. It is an error because the user named a specific target that no longer exists.
> - **AID validation fires before gate (BC-3.9.015 precondition)**: `^[0-9]+$` check on the AID argument MUST fire before the confirmation gate prompt. Do NOT show the prompt and then fail on bad AID.
> - **OQ-7 ruling (ID-only delete; no KEY)**: `jr issue attachment delete <AID>` takes the ATTACHMENT ID only, not a Jira issue key. The endpoint `DELETE /rest/api/3/attachment/{id}` does not require knowing which issue owns the attachment.
> - **BC-3.9.015 gate mechanics**: Same `eprint!`+`read_line` pattern as BC-3.9.014 (see S-576-3 AC-007). Three-way branch: `y`/`yes` → proceed; other → cancel, `"Deletion cancelled."` to stderr, exit 0; EOF/Err → exit 130.
> - **404 on bulk delete = benign skip (BC-3.9.010)**: When deleting multiple AIDs (bulk path), 404 on one AID is a benign skip (stale/already-deleted), NOT an error. If ALL AIDs 404, returns `{"count":0,"deleted":false,"ids":[]}`.
> - **--older-than uses dedicated `parse_age_duration` in `src/cli/issue/attachments.rs` (NOT `src/duration.rs` arithmetic)**: `jr issue attachment delete --issue <KEY> --older-than 30d` uses a dedicated `parse_age_duration` function implemented as a **`src/cli/issue/attachments.rs` private helper** (NOT a `src/duration.rs` sibling — `src/duration.rs` is read for **syntax-style precedent only** and MUST NOT be modified). `d` = 24 clock-hours (NOT 8-hour Jira workday); `w` = 7×24h. Boundary pin: `parse_age_duration("1d") == chrono::Duration::hours(24)` (unit test required). Cutoff type: `chrono::DateTime`; compare against attachment `created` field. Attachment list fetched via `GET /rest/api/3/issue/{key}?fields=attachment`.

On dry-run, no DELETEs issued. EC-3.9.020-7/8 are upload-path ECs and do NOT apply here — delete dry-run ECs are EC-3.9.020-1/2/3.

## Acceptance Criteria

### AC-001 (traces to BC-3.9.008 postcondition: DELETE endpoint; AID validation; 204/200 success)

`jr issue attachment delete <AID>` issues `DELETE /rest/api/3/attachment/{id}`.

AID validation: `^[0-9]+$` regex check BEFORE any prompt or HTTP call (BC-3.9.015 precondition). Non-numeric AID → exit 64: `"invalid attachment id: '<VALUE>' (must be numeric)"`.

On 204 or 200 (success): proceeds to JSON/human output.
On 404 (targeted single-AID delete, DEC-168 / EC-3.9.008-2 ~3469): exit 64 + stderr MUST BEGIN with `"Attachment <AID> not found or not accessible."` followed by the Jira error body as detail. NOT body-only; NOT silent exit 0.
On 401: exit 2. On 403: exit 1.

### AC-002 (traces to BC-3.9.015 postcondition: single-AID gate; AID validation before gate; VP-576-002)

Single-AID confirmation gate (BC-3.9.015; VP-576-002):

AID validation fires FIRST (before prompt or any HTTP call). Then, on the interactive TTY path, a pre-prompt metadata GET fires:

**Step 1**: `GET /rest/api/3/attachment/{id}` to retrieve `filename`. Failure paths:
- 404 → exit 64: `"Attachment <AID> not found or not accessible."` (no DELETE issued; no prompt shown)
- 403 → exit 1: `"Permission denied: cannot access attachment <AID>."` (no prompt)
- 401 → exit 2 (`JrError::NotAuthenticated`)
- 5xx/network → exit 1

**Step 2**: Prompt (via `eprint!` not `eprintln!` or `dialoguer`; trailing space, no newline):
```
Delete attachment <filename> (<AID>)? [y/N] 
```
`<filename>` MUST be display-sanitized per BC-2.7.011 display-sanitization primary clause (v1.3.94) before writing to the TTY (SEC-576-011 — CWE-116). Do not restate the character set here — see BC-2.7.011.

Three-way branch (P14-001/EC-3.9.015):
- `"y"`/`"yes"` (case-insensitive, after trim): proceed with DELETE.
- Any other non-empty text, or empty Enter (`Ok(n)`, n ≥ 1, buffer `"\n"`): `"Deletion cancelled."` to stderr, exit 0.
  - JSON mode (`--output json`): stdout `{"cancelled": true, "deleted": false}` via `output::render_json` (#526 invariant).
- EOF — `read_line` returns `Ok(0)` — or any `Err(_)`: exit 130 (`JrError::Interrupted`).

**`--yes` flag**: bypasses the gate entirely; the pre-prompt metadata GET is NOT issued (its sole purpose is the prompt filename — DELETE only, per BC-3.9.008 / BC-3.9.015 step 3).

**Non-interactive path** (`--no-input` OR stdin not a TTY, without `--yes`): exit 64; stderr: `"Use --yes to confirm deletion without a prompt."` No DELETE issued.

**VP-576-002**: Two tests must be in `tests/attachment_delete.rs`:
- `test_vp_576_002_delete_gate_confirm_proceeds`: confirm variant (y) proceeds to DELETE.
- `test_vp_576_002_delete_gate_cancel_stays`: cancel variant (n) exits 0, no DELETE issued.

Uses `JR_STDIN_IS_TTY=1` seam for interactive-branch tests.

- **Tests:** `tests/attachment_delete.rs::test_bc_3_9_015_aid_validation_before_gate`; `test_vp_576_002_delete_gate_confirm_proceeds`; `test_vp_576_002_delete_gate_cancel_stays`; `tests/attachment_delete.rs::test_bc_3_9_015_gate_eof_exits_130`

### AC-004 (traces to BC-3.9.016 EC-3.9.016-1/-8: --yes required for bulk paths; BC-3.9.013: fail-soft on bulk 404; all-404 benign; BC-3.9.010 EC-3.9.010-4/-5: non-404 failure abort + all-404 benign hint)

`jr issue attachment delete <AID1> <AID2> ... --yes` (multiple positional AIDs) or `jr issue attachment delete --issue <KEY> --yes`:

- `--yes` is REQUIRED for any bulk delete path (BC-3.9.016). Absence of `--yes` on bulk (without `--dry-run`) → exit 64 with the canonical BC-3.9.016 string for the form:
  - `--older-than` form (EC-3.9.016-1): `"--older-than requires --yes to confirm bulk deletion."`
  - multi-AID form (EC-3.9.016-8): `"--yes is required to delete multiple attachments without a confirmation prompt."`
- Issues one `DELETE /rest/api/3/attachment/{id}` per AID, sequentially. Fail-soft: 404 on one AID = benign skip (already deleted / stale). Non-404 errors (403/401/5xx/network) on any AID ABORT the sequence and surface the error (EC-3.9.010-4 / BC-3.9.013); already-completed deletions are not reversed.
- All-404 → JSON: `{"count":0,"deleted":false,"ids":[]}` (always emitted, exit 0) + human-mode hint to stderr: `"No attachments deleted (all were already removed or not found)."` (EC-3.9.010-5 HINT classification — JSON-suppressed; human mode only; exit 0). The hint string MUST match EC-3.9.010-5 verbatim.
- Partial success: `{"count":N,"deleted":true,"ids":[<succeeded AIDs>]}`.

- **Test:** `tests/attachment_delete.rs::test_bc_3_9_013_bulk_delete_fail_soft_all_404`
- **Test:** `tests/attachment_delete.rs::test_bc_3_9_016_bulk_requires_yes_exits_64` — asserts BOTH canonical EC-3.9.016 missing-`--yes` strings + exit 64 + zero DELETE issued, one sub-case per form: (a) `--issue <KEY> --older-than 30d` without `--yes` → stderr contains `"--older-than requires --yes to confirm bulk deletion."` (EC-3.9.016-1); (b) `<AID1> <AID2>` without `--yes` → stderr contains `"--yes is required to delete multiple attachments without a confirmation prompt."` (EC-3.9.016-8).
- **Test:** `tests/attachment_delete.rs::test_bc_3_9_010_bulk_delete_non_404_aborts_sequence` — two-AID delete (`<AID1> <AID2> --yes`); first DELETE returns 204 (success); second DELETE returns 403; assert: sequence stops after second DELETE (no further DELETEs issued), first deletion already completed and not reversed, 403 error surfaced to stderr, exit 1 (EC-3.9.010-4 / BC-3.9.013).
- **Test:** `tests/attachment_delete.rs::test_bc_3_9_010_bulk_partial_404_skip_continues` — three-AID delete (`<AID1> <AID2> <AID3> --yes`); AID1→204, AID2→404 (benign skip), AID3→204; assert: all 3 DELETEs issued, AID2 excluded from response ids, result `{"count":2,"deleted":true,"ids":["<AID1>","<AID3>"]}`, exit 0.

### AC-006 (traces to BC-3.9.016 + BC-3.9.019 postcondition: --issue KEY + --older-than; all AIDs collected)

`jr issue attachment delete --issue <KEY> --older-than <DUR> --yes` is the ONLY valid `--issue` form. `--issue` without `--older-than` → exit 2 (clap `requires` constraint; EC-3.9.016-9).

Wire flow:
1. Fetch `GET /rest/api/3/issue/{key}?fields=attachment` to get attachment list.
2. Extract all AIDs from `fields.attachment[].id`.
3. Parse `<DUR>` via `parse_age_duration` (see AC-007). Apply age filter: select attachments where `created < cutoff`.
4. Issue DELETE for each filtered AID (bulk path: 404-fail-soft per AC-004; non-404 aborts sequence per EC-3.9.010-4).

Human-mode output (N > 0): Before the first DELETE, emit to stderr: `"Deleting N attachment(s) older than <duration> from <KEY>."` (BC-3.9.019 pre-deletion HINT — human-only, JSON-suppressed). After all DELETEs complete, emit success summary: `"Deleted N attachment(s) older than <duration> from <KEY>."` (BC-3.9.019 success summary — human-only, JSON-suppressed). With `--output json`: NEITHER string is emitted to stderr.

KEY 404 (issue not found) → exit 64 before any DELETE. Zero matches (no attachments or none older than duration) → exit 0; human-mode stderr: `"No attachments older than <duration> found on <KEY>."` (BC-3.9.019 zero-match echo — human-only, JSON-suppressed); JSON: `{"count":0,"deleted":false,"ids":[]}`.

- **Test:** `tests/attachment_delete.rs::test_bc_3_9_019_issue_key_older_than_resolution` — extend with explicit sub-assertions for all three BC-3.9.019 canonical strings: (a) N>0 human run → stderr contains `"Deleting N attachment(s) older than <duration> from <KEY>."` (pre-first-DELETE HINT) AND output contains `"Deleted N attachment(s) older than <duration> from <KEY>."` (success summary); (b) same N>0 run with `--output json` → NEITHER string on stderr (both JSON-suppressed); (c) zero-match human run → stderr contains `"No attachments older than <duration> found on <KEY>."` (zero-match echo, JSON-suppressed). No new test fn; all three cases as sub-assertions within the single test.

### AC-007 (traces to BC-3.9.019 postcondition: --older-than duration parsing via parse_age_duration; EC-3.9.019-3/8)

`jr issue attachment delete --issue <KEY> --older-than <DUR> --yes`:
1. Fetch attachment list (same as AC-006 step 1).
2. Parse `<DUR>` via **dedicated `parse_age_duration` function** (e.g. `30d`, `2w`, `1h`, `30m`) — NOT `src/duration.rs` conversion logic. Calendar semantics (BC-3.9.019 verbatim): `d` = 24 clock-hours (NOT 8-hour Jira workday), `w` = 7×24h. Invalid/malformed duration → exit 64; canonical error string (EC-3.9.019-3): `"invalid duration: '<VALUE>'. Use formats like 30m, 2h, 1d, 7d, 2w."` (no reference to duration.rs error message, which may differ).
3. Compute cutoff = `now() - duration`. Filter to attachments where `created < cutoff` (older than the cutoff). `created` field is ISO 8601 string; parse via `chrono`. Unparseable `created` → skip that attachment with a stderr warning, do not abort.
4. Delete only the filtered AIDs (bulk path: 404-fail-soft per AC-004; non-404 aborts per EC-3.9.010-4). No matches → exit 0, `{"count":0,"deleted":false,"ids":[]}`.

**EC-3.9.019-8 boundary pin** (unit test MUST assert this): `parse_age_duration("1d") == chrono::Duration::hours(24)`. A worklog-style 1d=8h is WRONG for this function.

Cutoff is computed at the time the attachment list is fetched (not at CLI parse time — the difference is negligible but the implementation must be deterministic).

- **Test:** `tests/attachment_delete.rs::test_bc_3_9_019_older_than_parse_age_duration_filter`
- **Unit Test (src):** `src/cli/issue/attachments.rs #[cfg(test)]::test_bc_3_9_019_ec_8_parse_age_duration_1d_is_24h` — `parse_age_duration` is a PRIVATE helper; integration tests cannot call it directly; EC-3.9.019-8 (~3862) mandates "A unit test in src/ MUST assert this" (mirroring S-576-2's src-located sanitizer unit suite)

### AC-016 (traces to BC-3.9.013 postcondition: delete error taxonomy — AID 404 exit 64 + DEC-168 body; 401/403/5xx/network standard exits)

Full error taxonomy for `attachment delete` (BC-3.9.013):

| Error condition | HTTP | Exit code | Stderr content |
|---|---|---|---|
| Invalid AID (non-numeric) | — | 64 | `"invalid attachment id: '<VALUE>' (must be numeric)"` (no HTTP; cross-ref AC-001/AC-002) |
| Attachment not found (targeted single-AID) | 404 | 64 | DEC-168: stderr BEGINS with `"Attachment <AID> not found or not accessible."` then Jira error body (EC-3.9.008-2; cross-ref AC-001/AC-013) |
| Insufficient permissions | 403 | 1 | Jira error body surfaced |
| Not authenticated | 401 | 2 | stderr contains `"Not authenticated"` AND `"jr auth login"` (full literal: `Not authenticated. Run "jr auth login" to connect.` — `src/error.rs::JrError` + `client.rs`) |

**Multi-delete 404 exception** (BC-3.9.013 / AC-004): on multi-AID bulk and `--issue+--older-than` paths, a 404 on an individual DELETE is treated as already-deleted (benign) and silently skipped. The invalid-AID row and the AID 404 + DEC-168 row are already covered by named tests in AC-001/AC-002/AC-013. This AC adds dedicated coverage for the remaining taxonomy rows (401/403/5xx/network):
