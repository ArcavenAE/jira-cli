# S-SOH-589-1: tolerate id-absent editmeta allowedValues in `issue edit --field`

**Bundle**: SOH-BUGS-1
**GitHub issue**: #589
**BC anchors**: BC-3.4.015 (AllowedValue.id Option<String> type contract), BC-3.4.016 (EC-3.4.016-8 id-absent exit-64), BC-3.4.017 (VP-396-008 dry-run sub-case)
**VPs**: VP-589-001 (new), VP-396-002 (clarified), VP-396-008 (extended)
**Routing**: standard bug-fix (NOT quick-dev — 2 files, new EC, MED regression risk)

---

## Narrative

- **As a** developer editing Jira issues with custom fields that use user/group picker types
- **I want** `jr issue edit KEY --field NAME=VALUE` to succeed even when the issue's
  editmeta response includes `allowedValues` entries without an `id` field
- **So that** GDPR-era Jira instances (where user/group pickers carry `accountId` instead
  of `id`) do not crash `--field` edits on unrelated fields, making the feature actually
  usable on modern Jira Cloud instances

---

## Problem

`AllowedValue.id` in `src/types/jira/editmeta.rs` is typed as a required `String`. The
Jira Cloud OpenAPI schema for `allowedValues` entries has NO required properties —
GDPR-era user/group picker fields carry `accountId` instead of `id`. When serde
deserializes the `HashMap<String, EditMetaField>` from `GET /rest/api/3/issue/KEY/editmeta`,
a single id-absent `allowedValues` entry on ANY field (not just the one the user targets)
causes a `"missing field 'id'"` serde error, propagated as exit 1.

**Blast radius:** the entire `issue edit --field` feature is blocked whenever the issue
has a user/group picker on its Edit screen, regardless of which field the user targets.
The `--dry-run` path is equally blocked because the failure occurs before any mutation is
attempted. Seven surveyed Jira client libraries all use loose typing for `allowedValues`;
required `id: String` is an ecosystem outlier.

---

## Solution

Minimum-viable scope (approved by F1 delta analysis, DO NOT EXPAND):

1. **`src/types/jira/editmeta.rs`** — change `AllowedValue.id: String` → `Option<String>`.
   `name` and `value` are already `Option<String>` — this aligns `id` with the same
   lenient posture. No other `AllowedValue` field changes.

2. **`src/cli/issue/field_resolve.rs`** — 7 `av.id` call sites made Option-aware per the
   site table below. No logic changes beyond Option handling.

3. **`tests/issue_edit_field.rs`** — new tests covering the integration behaviors
   and the unit deserialization contract.

4. **`CHANGELOG.md`** — Fixed entry under `[Unreleased]` citing #589 (mandatory delivery
   task).

| Symbol | Context | Option-Handling Strategy |
|--------|---------|--------------------------|
| `resolve_edit_fields § id-bypass predicate` | `av.id == value` — id-bypass predicate | `av.id.as_deref().map(\|id\| id == value).unwrap_or(false)` — None silently excluded |
| `§ id-bypass wire emission` | `json!({"id": av.id})` — id-bypass wire emission | Exit 64 with EC-3.4.016-8 message if `id` is `None` post-match |
| `§ exact-match wire emission` | `json!({"id": av.id})` — exact-match wire emission | Exit 64 with EC-3.4.016-8 message if `id` is `None` post-match |
| `§ ambiguity display (exact)` | `format!("... (id: {})", av.id)` — ambiguity display, exact branch | `.as_deref().unwrap_or("<no-id>")` |
| `§ not-found label fallback` | `av.value.clone().unwrap_or_else(\|\| av.id.clone())` — fallback label, not-found error | `.unwrap_or_else(\|\| "<no-id>".to_string())` |
| `§ ambiguity display (substring)` | `av.id` — ambiguity display, substring branch | `.as_deref().unwrap_or("<no-id>")` |

   `mod.rs` re-exports — none of these files should change. The fix is contained to
   `editmeta.rs` (type) + `field_resolve.rs` (7 sites).

   sites MUST contain the substrings `"no machine-readable id"` AND `"--field"`. These
   are asserted by AC-002 and are cited in the BC. Do NOT paraphrase or omit them.

   paths (ambiguity + not-found messages). They MUST NOT exit 64 for a `None` id — their
