# S-576-2: `jr issue attachment download` — single/batch/newest + streaming + CWE-22 sanitization

## Narrative

- **As a** developer or CI script using `jr` against Jira issues
- **I want** `jr issue attachment download <KEY>` to stream attachments to disk with a safe default path, supporting single-file (`--id`), batch (`--all`), and newest-N (`--newest N`) selectors
- **So that** I can retrieve large attachments without memory exhaustion, with server-supplied filenames sanitized against path-traversal attacks (CWE-22)

## Acceptance Criteria

### AC-001 (traces to BC-2.7.007 postcondition: two-step wire path; streaming; no ?redirect=false)

`jr issue attachment download <KEY> --id <AID>` issues:
1. Step 1: `GET /rest/api/3/attachment/{id}` (metadata; tolerates partial struct — missing fields do not abort per P26-003).
2. Step 2: `GET /rest/api/3/attachment/content/{id}` (content; follows 302/303 redirects; MUST NOT append `?redirect=false` — JRACLOUD-97046; `Authorization` header is stripped by reqwest on cross-host redirect per GHSA-9857-6MW7-FQ2M — correct behavior).

Response body is streamed chunk-by-chunk via `bytes_stream()` (ADR-0017 reqwest `stream` feature) to a temp file, then atomic-rename to the final path. On error mid-stream: temp file deleted, exit 1 (EC-2.7.007-4). On Ctrl+C/SIGINT: temp file deleted, exit 130 (EC-2.7.007-5 best-effort; `tokio::signal::ctrl_c()` implementation note).

A wiremock test MUST assert the `Authorization` header is ABSENT from the redirect-target request (SEC-576-003 / BC-2.7.007 EC-2.7.007-3 / CWE-522).

- **Tests:** `tests/attachment_download.rs::test_bc_2_7_007_two_step_streaming_wire_path`; `tests/attachment_download.rs::test_bc_2_7_007_no_redirect_false_param`; `tests/attachment_download.rs::test_bc_2_7_007_auth_absent_on_redirect_target`

### AC-002 (traces to BC-2.7.007 postcondition: --out pre-flights before metadata GET; P32-001)

For single-`--id` with `--out <PATH>`:
1. Local pre-flights fire BEFORE step-1 metadata GET (P32-001 fail-cheap-first principle):
   - EC-2.7.007-6: `--out` parent directory does not exist → exit 64: `"Output directory does not exist: <parent>"` before HTTP.
   - EC-2.7.007-11: `--out` path is an existing directory → exit 64: `"output path is a directory: <PATH>"` before HTTP.
   - EC-2.7.007-12: `--out` path is an existing regular file AND `--force` absent → exit 64: `"File already exists: <path>. Use --force to overwrite."` before HTTP (SEC-576-010).
2. On double-fault (local check fails), the local check's error message wins.
3. **`--force` bypass**: when `--force` is supplied and `--out <PATH>` targets an existing file, the overwrite-refuse check (EC-2.7.007-12) is skipped and the file is overwritten silently on download completion.

Without `--out`, the unconditional step-1 metadata GET runs (to obtain filename for path computation).

- **Test:** `tests/attachment_download.rs::test_bc_2_7_007_out_preflight_before_get_p32_001`

### AC-004 (traces to BC-2.7.011 postcondition: sanitize_attachment_filename CWE-22 disk-path algorithm)

`sanitize_attachment_filename(name: &str) -> Option<String>` implements the BC-2.7.011 5-step CWE-22 disk-path algorithm (verbatim from BC-2.7.011 lines 902-911):

1. **Basename extraction**: `Path::new(name).file_name()` — strips any directory component (`../../etc/passwd` → `"passwd"`; `/etc/passwd` → `"passwd"`; `C:\Windows\system32\calc.exe` → `"calc.exe"`). If `file_name()` returns `None` (path ends in `..` or reduces to empty) → return `None`.
2. **Pseudo-name rejection**: if the extracted basename as a `Path` component equals `"."` or `".."` → return `None`. Empty string after OsStr conversion → return `None`.
3. **NUL byte rejection**: if the name contains a NUL byte (`\0`) → return `None`. NUL terminates strings in OS path APIs; this is a REJECTION (return None), NOT a strip operation.
4. **Character scrub**: REPLACE any remaining `/`, `\`, or `:` in the string with `_`. These are path separators on various platforms. This is a REPLACEMENT with underscore, NOT a strip.
5. **Length cap** (UTF-8-safe): truncate to at most 214 bytes on a valid UTF-8 character boundary (`floor_char_boundary` semantics — never split a multi-byte codepoint). Step 5.5 (SEC-576-007): strip trailing ASCII whitespace characters and trailing `.` from the basename after the length cap.

Returns `Some(sanitized_name)` if all steps produce a non-empty string; otherwise `None`. Fallback to id-as-filename per BC-2.7.010 degenerate case when `None` is returned.

**Windows device names (SEC-576-001 — caller responsibility, NOT this function)**: `sanitize_attachment_filename` does NOT handle Windows device names. The expected results are: `"CON"` → `Some("CON")`; `"NUL"` → `Some("NUL")`; `"COM1"` → `Some("COM1")`; `"nul.txt"` → `Some("nul.txt")`. Device-name escape is the **caller's** responsibility — batch paths get an automatic SHA-1 prefix that disambiguates device names; single-id bare paths need an explicit `_` prefix escape at the call site.

**Containment check** (BC-2.7.011 two-step, SEC-576-002): `canonicalize(out_dir)` + `path.starts_with(out_dir_canonical)`. This check MUST NOT be applied to `--out <PATH>` (trusted operator input — BC-2.7.011 P25-002). **Mutation exemption**: the containment check is intentionally unreachable via any API-supplied filename after steps 1–5; surviving mutants on this path are accepted-class (annotate branch with `// BC-2.7.011 defense-in-depth: unreachable via API-supplied filenames after sanitization steps 1-5`).

**Unit tests** in `src/cli/issue/attachments.rs #[cfg(test)]` MUST cover at minimum (BC-2.7.011 "Unit test coverage required" list):
- `"../../etc/passwd"` → `Some("passwd")` (path traversal stripped)
- `"/etc/passwd"` → `Some("passwd")` (absolute path stripped)
- `"C:\\Windows\\system32\\calc.exe"` → `Some("calc.exe")` (Windows path stripped)
- `"."` → `None`; `".."` → `None`; empty string → `None`
- NUL-containing string (e.g. `"foo\0bar"`) → `None` (NOT `Some("foobar")`)
- Filename with `:` (e.g. `"C:config.txt"`) → `Some("C_config.txt")` (colon replaced, NOT stripped)
- `"CON"` → `Some("CON")` (device name passes through — caller escapes)
- `"NUL"` → `Some("NUL")`; `"COM1"` → `Some("COM1")`; `"nul.txt"` → `Some("nul.txt")`
- Filename exceeding 255 bytes → length ≤ 214 bytes
- Multi-byte UTF-8 codepoint at truncation boundary (214-byte ASCII prefix + 3-byte `é`) → `Some(214-byte prefix)` (char dropped, not split)
- Trailing dot/space strip (e.g. `"foo. "` → `Some("foo")`)

These are inline unit tests in `#[cfg(test)]`, not wiremock.

**VP-576-001**: see AC-014.

- **Tests:** `src/cli/issue/attachments.rs #[cfg(test)]` unit suite; `prop_sanitize_attachment_filename_no_path_traversal` proptest

### AC-005 (traces to BC-2.7.010 postcondition: default output path computation)

Default output path computation (no `--out` flag):
- Batch (`--all` / `--newest`): `<out-dir>/<sha1-of-attachment-id>_<sanitize_attachment_filename(filename)>`. SHA-1 prefix is 40 hex chars + `_` + sanitized basename. Combined length ≤ 255 bytes (41 + 214 = 255 ≤ NAME_MAX per ADV-010). When `sanitize_attachment_filename` returns `None` (degenerate name), use id itself as the basename.
- Single `--id`: bare `sanitize_attachment_filename(filename)` in cwd (or `--out` override if supplied).

Server-ID trust assumption: the `id` from the Jira API is not independently validated for use in the SHA-1 computation — it is trusted as numeric per BC-2.7.010 SEC-576-008 note.

- **Test:** `tests/attachment_download.rs::test_bc_2_7_010_default_path_sha1_prefix_batch`

### AC-006 (traces to BC-2.7.007 EC-2.7.007-7: filename=RAW / path=on-disk pairing; P27-001)

In the download manifest JSON (`--output json`):
- `downloaded[].filename` is the RAW Jira-supplied filename (pre-sanitization; per P27-001 deliberate pairing).
- `downloaded[].path` is the output path as-constructed by `jr` — NOT canonicalized, NOT made absolute (EC-2.7.007-7 / BC-2.7.010 P18-004 ruling). Snapshot tests MUST redact or normalize `path` (e.g., via a TempDir root substitution); exact-match assertions on `path` are only valid with a controlled current working directory.
- `downloaded[].size` is bytes-WRITTEN (from `tokio::io::copy` return count; P31-002), NOT the list-reported `fields.attachment[].size`.
- `downloaded[].id` is the attachment AID string.

JSON shape: `{"downloaded": [{"filename": <raw>, "id": "<AID>", "path": "<as-constructed path>", "size": <bytes-written>}]}`. Keys in BTreeMap-alphabetical order within each element.

Output routed through `output::render_json` (#526 invariant).

- **Test:** `tests/attachment_download.rs::test_bc_2_7_007_json_manifest_raw_filename_written_size_p27_p31`

### AC-007 (traces to BC-2.7.008 postcondition: --all batch download; fail-soft; out-dir existence)

`jr issue attachment download <KEY> --all --out-dir <DIR>`:
- Fetches attachment list via `GET /rest/api/3/issue/{key}?fields=attachment` (batch metadata source — BC-2.7.008).
- Downloads each attachment fail-soft: per-file errors emit to stderr (human mode) or as JrError elements in JSON mode; other files continue.
- `--out-dir` not-exist → exit 64 before download. `--out-dir` exists but not a directory → exit 64 (EC-2.7.008-4).
- Collision-skip (overwrite-refuse): when a file would overwrite an existing file, emits a collision-skip warning as a NON-ERROR hint — suppressed in JSON mode (P27-003 / §2.7 hint-vs-error taxonomy). The filename in the collision-skip warning MUST be display-sanitized via `display_sanitize_filename` (from S-576-1) before writing to stderr per BC-2.7.011 SEC-576-011 (CWE-116) — collision-skip warnings are a named display-sanitization call site.
- Empty issue (`--all` on issue with zero attachments): exit 0; JSON mode returns `{"downloaded":[]}` (EC-2.7.008-1 + EC-2.7.001-1 for JSON).
- `"Downloaded N of M attachments to <dir>."` summary fired in human mode ONLY (suppressed in JSON mode per P25-001 / §2.7 taxonomy). Verbatim from BC-2.7.008 line 795: the string MUST include `"to <dir>"` (the actual output directory path).

- **Test:** `tests/attachment_download.rs::test_bc_2_7_008_all_batch_fail_soft`

### AC-014 (traces to BC-2.7.011 VP-576-001: sanitize_attachment_filename proptest)

`prop_sanitize_attachment_filename_no_path_traversal` in `src/cli/issue/attachments.rs #[cfg(test)]`: the proptest domain MUST include non-ASCII-printable bytes (NUL, control chars) — not limited to ASCII-printable — so that step 3 (NUL → None) and step 4 (character scrub) are exercised by the random input generator.

For any arbitrary byte-string input (including NUL bytes and control characters), assert (VP-576-001 verbatim from BC-2.7.011 line 930):
1. No `Some(name)` result contains `/`, `\`, `:`, or a NUL byte.
2. `Some(name)` length in bytes is ≤ 214.
3. All `Some(name)` values are valid UTF-8 (`std::str::from_utf8` succeeds).
4. `"."`, `".."`, empty string, and NUL-byte inputs each return `None`.
5. `"../../etc/passwd"` → `Some("passwd")`; `"/etc/passwd"` → `Some("passwd")`.
6. A 214-byte ASCII prefix + 3-byte UTF-8 char returns `Some(214-byte prefix)` (char dropped, not split).
7. `"CON"` → `Some("CON")`; `"NUL"` → `Some("NUL")` (device names pass through — NOT rejected; caller escapes per SEC-576-001).

**Remove** any assertion that output "does not match Windows device names" — device names are expected `Some(name)` outputs per the BC.

Default proptest case count (~256); cap to 128 only on CI flake pressure.

- **Test:** `prop_sanitize_attachment_filename_no_path_traversal` (proptest in `src/cli/issue/attachments.rs`)

### AC-015 (traces to BC-2.7.010 SEC-576-011 postcondition: display_sanitize_filename required in degenerate-name warning)

When `sanitize_attachment_filename(name)` returns `None` (degenerate name — empty, `"."`, `".."`, NUL-containing, etc.) and the id-as-filename fallback is used, the degenerate-name warning emitted to stderr MUST display-sanitize the raw `<raw>` value via `display_sanitize_filename` BEFORE writing to the TTY (BC-2.7.010 ~line 870, SEC-576-011, CWE-116). The warning format is:

`"warning: using id as filename for attachment <AID> — original name '<display-sanitized-raw>' could not be sanitized."`

The `<raw>` string in the warning is the **display-sanitized** form (CWE-116 terminal injection prevention), not the verbatim Jira-supplied name. This applies to both human mode and JSON mode (the warning is a stderr emission; however, per §2.7 hint taxonomy, it is a NON-ERROR hint and therefore suppressed in JSON mode).

- **Test:** `tests/attachment_download.rs::test_bc_2_7_010_degenerate_name_warning_display_sanitized`

### AC-016 (traces to BC-2.7.011 SEC-576-001 postcondition: Windows device-name escape at single-id call site)

At the **single-id** bare-naming call site (the path where `sanitize_attachment_filename` returns `Some(name)` and the name is used as the output filename for `--id` without a SHA-1 prefix), the caller MUST check whether the sanitized basename (the portion before the first `.`) is a Windows reserved device name (case-insensitive match: `CON`, `NUL`, `PRN`, `AUX`, `COM1`–`COM9`, `LPT1`–`LPT9`) and, if so, prepend `_` to produce `_CON`, `_NUL`, etc. (SEC-576-001: Windows NTFS/FAT32 reserved names; BC-2.7.011 ~line 915).

**Scope restriction**: This escape is applied at the single-id call site ONLY:
- Batch paths (`--all`, `--newest`) already have a 40-hex-char SHA-1 prefix that prevents device name conflicts — no additional escape needed.
- `--out <PATH>` paths are trusted operator input (BC-2.7.011 P25-002) — not subject to this escape.

`sanitize_attachment_filename` itself does NOT perform the device-name escape (it returns `Some("CON")`, `Some("NUL")` etc. — the caller is responsible per BC-2.7.011 P18-004).

- **Test:** `tests/attachment_download.rs::test_bc_2_7_011_windows_device_name_escape_single_id_call_site`

### AC-017 (traces to BC-2.7.007 required-group/EC-2.7.007-9 ~769; BC-2.7.008 EC-2.7.008-3 ~803; BC-2.7.009 body ~834/EC-2.7.009-1 ~836/EC-2.7.009-2: clap structural constraints + handler N-validation for download flags)

`jr issue attachment download` structural constraints split into two layers:

**Layer 1 — Clap parse-time constraints (all exit 2; clap error to stderr; no application code reached):**
- `download <KEY> --id <AID> --all` → exit 2 (`--id` and `--all` are mutually exclusive; EC-2.7.008-3 ~803).
- `download <KEY> --id <AID> --newest 3` → exit 2 (`--id` and `--newest` are mutually exclusive; BC-2.7.009 body ~834).
- `download <KEY> --all --newest 3` → exit 2 (`--all` and `--newest` are mutually exclusive; BC-2.7.009 body ~834).
- `download <KEY> --all --out /tmp/foo` → exit 2 (`--out` requires single-mode `--id`; EC-2.7.007-9 ~769).
- `download <KEY>` (no `--id`, no `--all`, no `--newest`) → exit 2 (at least one selector required; BC-2.7.007 required-group clause ~729).
- `download <KEY> --newest foo` (non-integer) → exit 2 (clap type-parse failure; EC-2.7.009-2).

**Layer 2 — Handler-level N-validation (exit 64; fired before any HTTP call; `allow_negative_numbers = true` so negative values pass clap and are caught here):**
- `download <KEY> --newest 0` → exit 64, message `"--newest requires a positive integer."` (EC-2.7.009-1 ~836; N = 0 fails N ≥ 1 guard).
- `download <KEY> --newest -3` → exit 64, same message and handler path (N ≤ 0 guard; `allow_negative_numbers = true` lets `-3` reach the handler).

- **Tests:** `tests/attachment_download.rs::test_bc_2_7_download_clap_structural_constraints` (6 clap exit-2 cases); `tests/attachment_download.rs::test_bc_2_7_009_newest_nonpositive_exits_64` (2 handler exit-64 cases: N=0, N=-3)
