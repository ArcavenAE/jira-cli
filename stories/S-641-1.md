# S-641-1 — MSRV floor self-enforcement guards (ADV-M4/M5/L3)

## Narrative

As a CI maintainer, I want:
1. The msrv job to assert — not merely assume — that the toolchain override took effect, so
   that a silent regression in `RUSTUP_TOOLCHAIN` precedence is caught immediately (ADV-M4).
2. A compile-time test that reads `Cargo.toml`'s `rust-version` as the canonical source and
   verifies all other MSRV declaration sites agree with it, so that the 8+ sites stay in sync
   and a future MSRV raise (S-640-1) is a single coordinated change the test then protects (ADV-M5).
3. A decided stance on the `comfy-table` exact-pin dependabot churn: either an `ignore` entry
   in `.github/dependabot.yml` or an explicit decision recorded in `Cargo.toml`, so that
   recurring red dependabot PRs do not train reviewers to dismiss msrv failures (ADV-L3).

## Problem Statement

**ADV-M4 (MEDIUM GAP) — msrv job produces no evidence that the toolchain override took effect:**
S-626-1 adds `RUSTUP_TOOLCHAIN: "1.85.0"` to the msrv job's `cargo check` step. The `env:` block
is echoed in the job log, but there is no step that asserts `rustc` is actually running at 1.85.0.
If `RUSTUP_TOOLCHAIN` precedence ever changes (rustup update, shim change, step reordering), the
job stays green — the failure mode S-626-1 was opened to prevent. Proposed one-line fix:

```yaml
- run: rustc --version && rustc --version | grep -q '^rustc 1\.85\.0 '
  env:
    RUSTUP_TOOLCHAIN: "1.85.0"
```

This step fails immediately if the override is not in effect. It is self-enforcing, not merely
self-documenting. Finding F7 (no negative-control test) is a coarser framing of the same gap —
ADV-M4's `rustc --version` assertion IS the negative-control. F7 is folded here.

**ADV-M5 (MEDIUM GAP) — MSRV floor asserted at 8+ string sites with no drift guard:**
Current declaration sites (as of S-626-1): `Cargo.toml` `rust-version`; `README.md` badge;
`ci.yml` job name; `ci.yml` `toolchain:` input; `ci.yml` `RUSTUP_TOOLCHAIN:` env; `ci.yml`
trailing comment; plus mentions in `CLAUDE.md` gotcha and `CHANGELOG.md`. Nothing enforces
agreement. The deferred MSRV raise (S-640-1) must change all of them atomically. This repo
has an established family for exactly this class of guard: `tests/claude_md_citations.rs`,
`tests/mutants_glob_existence.rs`, `scripts/check-bc-cumulative-counts.sh`. A toolchain/MSRV
guard is the idiomatic missing member.

**Critical design constraint (interlock with S-640-1):** the guard MUST read `Cargo.toml`
`rust-version` as the canonical source and verify the other sites agree with it — it must NOT
hard-code `"1.85.0"`. This way S-640-1 changes the canonical source and all derived sites
together; the guard then verifies they are in sync post-change. A guard that hard-codes the
version would itself block S-640-1 and require two simultaneous edits.

**M-003/S626P2 (scope addition, re-stated v0.3) — three workflow comments need re-tensing:**
The defensive `rustup target add` steps in `sign-and-publish.yml` (~:58-65) and
`backfill-release.yml` (~:73-79) carry adjacent comments. `release.yml` (~:43-45) has only a
bare step name — no E0463 comment block.

**Corrected assessment (S-626-1 v1.6 pass-3):** The mechanism described in the comments of
`sign-and-publish.yml` and `backfill-release.yml` is **confirmed** (see S-626-1 MEDIUM-002):
at the `1.85.0`-branch SHA, the action installed targets onto the 1.85.0 toolchain while
`cargo build` ran under stable (because `rust-toolchain.toml` outranks `rustup default`), so
those targets were absent from stable → E0463. The comments are **substantively correct**.

**What is stale post-fix:** With `toolchain: stable` in the S-626-1 fix now agreeing with the
toml, the target lands on the active toolchain — the three `rustup target add` steps are
**idempotent no-ops**. The present-tense claim "without this step the build fails" is now
historical. The fix (v0.2 scope) is therefore narrowed: do NOT rewrite to "root cause
unconfirmed" (that would be false); instead **preserve the causal explanation** and
**re-tense** the claim as historical, noting the steps are retained per P71-003/EC-1 as
defensive guards even though they are currently no-ops.

**Ordering constraint:** AC-4 must NOT be actioned before S-626-1 v1.6 (mechanism corrections)
is merged — implementers reading the v0.2 version of this story would produce an incorrect
rewrite (root cause unconfirmed) that contradicts the confirmed mechanism.

The `rustup target add` command lines themselves are NOT changed (P71-003 do-not-remove).
Also: `release.yml` ~:43-45 is a fourth `rustup target add` site not enumerated in S-626-1
AC-5 until the v1.5 correction — now correctly annotated as having no E0463 comment.

**ADV-L3 (LOW/operational) — `=7.2.1` pin has no dependabot `ignore` entry:**
`comfy-table 7.2.2` is already published and the 7-day cooldown has elapsed. Dependabot will
open — and re-open after each close — a PR bumping `=7.2.1` → `=7.2.2` until the MSRV is
raised. The failure is loud (red msrv job), not silent. But recurring red-on-routine-dep-bump
trains reviewers to discount msrv failures — precisely the signal S-626-1 just made
trustworthy. Decision required at elaboration: add an `ignore` entry to suppress churn until
S-640-1 lands, or accept the churn deliberately and record that decision in the pin comment.

**LOW-004 (LOW/refinement, S-626-1 pass-4) — `dtolnay/rust-toolchain` pin comments name the toolchain, not the action version:**
All 7 `dtolnay/rust-toolchain` pins carry trailing comments naming a **toolchain** (`# stable`,
`# 1.85.0`), whereas every other 40-char pin in the same files names the **action version**:
`actions/checkout@3d3c… # v7.0.1`, `Swatinem/rust-cache@e18b… # v2`,
`step-security/harden-runner@bf74… # v2.20.0`, `codecov/codecov-action@fb8b… # v6`,
`gitleaks/gitleaks-action@e0c4… # v3.0.0`, `EmbarkStudios/cargo-deny-action@3c63… # v2`.
Counter-precedent exists (`taiki-e/install-action@e5de… # cargo-llvm-cov` annotates purpose),
so the convention is not absolute — hence LOW.

Consequence worth recording: the pinned action's version stays unrecoverable from the pin line
— the precise opacity that let the 1.85.0-branch SHA masquerade as a master pin through 84 F2
passes, three Step 4.5 passes, and a PR review. And `# 1.85.0` is now redundant with
`toolchain: "1.85.0"` two lines below while saying nothing about the action.

**Not covered by existing ACs:** AC-4 audited whether `# 1.85.0` *agreed with* the toolchain
input, validating the toolchain-naming convention rather than questioning it. Six `# stable`
comments were the inaccurate ones; no AC checked those. Adding action-version comments is a
future maintenance note — not a requirement in this story's current scope.

### AC-1 (draft): rustc version assertion step added to msrv job (ADV-M4 + F7)

`.github/workflows/ci.yml` msrv job gains a new step — positioned BEFORE `cargo check` — that
asserts `rustc` is actually running at the declared MSRV:

```yaml
- name: Assert rustc version matches MSRV
  run: rustc --version && rustc --version | grep -q '^rustc 1\.85\.0 '
  env:
    RUSTUP_TOOLCHAIN: "1.85.0"
```

The step fails immediately if `RUSTUP_TOOLCHAIN` override is not in effect. The grep pattern
`'^rustc 1\.85\.0 '` anchors to the beginning and includes a trailing space to avoid matching
`1.85.0` as a prefix of `1.85.01` (hypothetical future patch).

**Note for S-640-1:** when S-640-1 raises the floor to 1.88, this step must be updated to
`grep -q '^rustc 1\.88\.0 '`. The AC-2 guard test (below) verifies this stays in sync.

*Traces to*: ADV-M4 (S-626-1 adversarial review); F7 folded (sharper framing)

### AC-2 (draft): Multi-site MSRV agreement guard test (ADV-M5)

`tests/msrv_toolchain_guard.rs` is created and rides the existing `test` job with no CI YAML
change (same pattern as `tests/claude_md_citations.rs`).

**What the test verifies (reading `Cargo.toml` `rust-version` as canonical — MUST NOT hard-code):**

1. `Cargo.toml` `rust-version` field is present and parses as a valid version string
   (canonical source; all other checks derive from this).
2. `README.md` contains the MSRV badge (`MSRV-{major}.{minor}` or `MSRV-{major}.{minor}.{patch}`).
3. `.github/workflows/ci.yml` msrv job `name:` contains the version string in `MSRV ({version})`
   format.
4. `.github/workflows/ci.yml` msrv job `toolchain:` input value matches the canonical version.
5. `.github/workflows/ci.yml` msrv job `RUSTUP_TOOLCHAIN:` env value matches the canonical version.
6. `Cargo.toml` `comfy-table` dependency is an exact pin (value starts with `=` or is a bare
   version without `^`, `~`, `>=`, or `*`; pin is load-bearing per S-626-1 AC-8 until S-640-1).
7. (Optional) Old stale SHA `c93f4f9c` is absent from all 6 workflow files (re-verify
   S-626-1 AC-7 post-delivery; exact assertion TBD at elaboration).

**Critical design rule:** every version comparison reads from `Cargo.toml` at test time. If
`Cargo.toml` says `rust-version = "1.88"`, the test verifies the ci.yml says `1.88`. The test
does not know or care what the floor is — it only checks agreement. Raising the floor for
S-640-1 is then a single coordinated edit; the guard confirms it was done everywhere.

**Let-chain detection form set (INFO-005, S-626-1 pass-4):** As written, AC-2 only checks MSRV
agreement across declaration sites — it does not scan the codebase for let-chain patterns. If
this guard is ever extended to verify the codebase contains no let-chains at the declared MSRV
floor, the **complete form set** must be used: `&& let` (condition-first form);
`^\s*&& ` (let-first continuation); `(if|while) let .*=.*&&` (inline); `^\s*|| ` (disjunctive).
`grep '&& let'` alone catches only the condition-first form and silently misses the let-first
form — which was exactly what `src/cli/auth/keychain.rs` contained pre-fix (`grep -c '&& let'
keychain.rs` = 0 on the broken version; `grep -cE '^\s+&& ' keychain.rs` = 1). A guard built
on the single-form grep would pass on a codebase that still contains let-first let-chains.

*Traces to*: ADV-M5 (S-626-1 adversarial review); INFO-005 (S-626-1 pass-4)
