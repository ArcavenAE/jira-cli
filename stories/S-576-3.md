> - **ADR-0017 Cargo.toml delivery slot**: `Cargo.toml` gains reqwest `multipart` feature and `tokio-util = { version = "^0.7", features = ["io-util"] }` direct dep in THIS story (S-576-3). > - **X-Atlassian-Token: no-check IS MANDATORY on upload**: Jira Cloud triggers an XSRF-related rejection when this header is absent on multipart POST. Never omit it. Atlassian's exact body text varies by deployment and is not load-bearing — jr only guarantees the header is always sent; the test asserts header presence, not the server's 403 body (BC-3.9.001 v1.3.87 hedge, P12-003).
> - **Retry requires fresh ReaderStream per attempt**: `Request::try_clone()` returns `None` for multipart requests (ADR-0017). On retry (rate-limit 429), the entire request including the `ReaderStream` must be rebuilt. This is a STREAMING-ONLY constraint — the stream is consumed on the first attempt.
> - **stdin `-` rejected (EC-3.9.001-6)**: `jr issue attachment upload <KEY> -` exits 64 with `"stdin upload is not supported; provide a file path."` (BC-3.9.001 EC-3.9.001-6 canonical). Do NOT implement stdin upload.
> - **BC-3.9.014 gate mechanics**: Confirmation prompt uses `eprint!` (NOT `eprintln!`, NOT `dialoguer::Confirm`). Three-way branch: `y`/`yes` (case-insensitive) → proceed; other input → cancel, exit 0; EOF (read_line Ok(0)) or Err(_) → exit 130 (P14-001). Prompt ends with `[y/N] ` (no newline after `] `).
> - **EC-3.9.020-7 / EC-3.9.020-8 / EC-3.9.020-9 dry-run three-category taxonomy**: `--dry-run` SUPPRESSES **confirmation gates** (EC-3.9.020-7) — guard destructive actions ("proceed with `--replace-existing`?"). Pre-flight checks are a THIRD distinct category; do not conflate with eligibility guards. EC-3.9.020-9 verbatim taxonomy is authoritative.

## Acceptance Criteria

### AC-001 (traces to BC-3.9.001 postcondition: multipart POST; X-Atlassian-Token mandatory; ReaderStream)

`jr issue attachment upload <KEY> <FILE>` issues:
`POST /rest/api/3/issue/{key}/attachments` with:
- `Content-Type: multipart/form-data` (reqwest `multipart` feature; field name `"file"`).
- `X-Atlassian-Token: no-check` header MANDATORY on every upload request (XSRF-related rejection when absent; Atlassian's exact body text varies by deployment and is not load-bearing — jr only guarantees the header is always sent; the test asserts header presence, not the server's 403 body).
- File streamed via `tokio_util::io::ReaderStream` (ADR-0017 `io-util` feature). No client-side size cap.

On 429 (rate-limit): retry requires rebuilding the entire multipart request (including a fresh `ReaderStream` from a fresh `tokio::fs::File::open` call — `Request::try_clone()` returns `None` for multipart; ADR-0017 constraint).

`stdin -` as FILE value → exit 64 before HTTP: `"stdin upload is not supported; provide a file path."` (EC-3.9.001-6 canonical).

`allow_hyphen_values = true` on FILE clap arg (CLAUDE.md §allow_hyphen_values gotcha — permits filenames starting with `-`).

- **Tests:** `tests/attachment_upload.rs::test_bc_3_9_001_multipart_post_x_atlassian_token_mandatory`; `tests/attachment_upload.rs::test_bc_3_9_001_stdin_rejected`; `tests/attachment_upload.rs::test_bc_3_9_001_rate_limit_retry_rebuilds_request`

### AC-002 (traces to BC-3.9.001 EC-3.9.001-4 precondition: FILE arg pre-checks before HTTP; exit 64; BC-3.9.012 EC-3.9.012-1 for file-not-found taxonomy row)

FILE arg pre-checks fire BEFORE any HTTP call (BC-3.9.001 EC-3.9.001-4; BC-3.9.012):
- File path does not exist or is not a regular file (checked via `is_file()`) → exit 64: `"file not found: <path>"` (missing) or `"not a regular file: <path>"` (exists but not a regular file — directory, symlink-to-dir, FIFO, block device, etc.).
- Stdin `-` as FILE → exit 64: `"stdin upload is not supported; provide a file path."` (EC-3.9.001-6 canonical).

For multi-file invocations (BC-3.9.018), ALL file pre-checks run before any HTTP is issued (fail-fast-all).

- **Test:** `tests/attachment_upload.rs::test_bc_3_9_001_file_prechecks_before_http`

### AC-003 (traces to BC-3.9.009 postcondition: upload JSON shape; VP-576-004 upload half)

`jr issue attachment upload <KEY> <FILE> --output json` returns a **bare JSON array** (BC-3.9.009 — no envelope wrapper):
```json
[{"author": {"accountId": "<id>", "displayName": "<name>"}, "contentUrl": "<url>", "created": "<iso>", "filename": "<name>", "id": "<AID>", "mimeType": "<type>", "size": <bytes>}]
```

Shape: BC-2.7.002 curated form `{author, contentUrl, created, filename, id, mimeType, size}` — BTreeMap-alphabetical key order. `"self"` field is OMITTED. `"content"` from Jira response is renamed to `"contentUrl"` (VP-576-004 curated-serialization invariant — same `serialize_attachment_curated` helper established in S-576-1). Multi-file: array with one element per file in upload order (EC-3.9.009-2).

**VP-576-004 upload half**: The upload response uses the identical curated shape as the list response (both via `serialize_attachment_curated`). A dedicated cross-path integration test (`test_vp_576_004_curated_shape_upload_and_list_are_structurally_identical`) MUST assert that both paths use the same shape by constructing both output types from the same fixture data and comparing key sets.

Output routed through `output::render_json` (#526 invariant).

- **Tests:** `tests/attachment_upload.rs::test_bc_3_9_009_upload_json_shape_self_omitted_content_renamed`; `tests/attachment_upload.rs::test_vp_576_004_curated_shape_upload_and_list_are_structurally_identical`

### AC-004 (traces to BC-3.9.001 postcondition: human-mode upload echo; P19-I1 4-column table)

`jr issue attachment upload <KEY> <FILE>` (no `--output json`) prints:
- On success: a table row per uploaded file with columns: **Filename** (via `display_sanitize_filename` — CWE-116 terminal display), **Size** (human-readable: `1.2 MB`, `42 KB`, `815 B`), **ID**, **Created** (BC-3.9.001 P19-I1 note: 4-column upload echo table — deliberately differs from the 6-column list table; no Type/MIME column on the upload echo surface).

> **PRE-F4-UNICODE-DISPLAY-SANITIZATION**: `display_sanitize_filename` in the table cells and prompt output currently strips only ASCII control characters and null bytes. Unicode bidi-override controls (U+202E etc.) and line separator (U+2028/29) are out of scope for v1.3.81. When this spec extension ships (PRE-F4), this function gains additional Unicode normalization. Implementer: do NOT add Unicode filtering here — wait for F4.

Per-file errors print to stderr. Partial success (some files succeed, some fail) exits 1. All success exits 0.

- **Test:** `tests/attachment_upload.rs::test_bc_3_9_001_human_table_display`

### AC-005 (traces to BC-3.9.001 EC-3.9.001-2 postcondition: multi-file = single multipart POST)

`jr issue attachment upload <KEY> <FILE1> <FILE2> ...` sends a **single multipart POST** (`POST /rest/api/3/issue/{key}/attachments`) with multiple `file`-named parts, one per FILE, in the order supplied on the command line (BC-3.9.001 EC-3.9.001-2). This is NOT one POST per file.

### AC-006 (traces to BC-3.9.017 postcondition: --replace-existing: list→match→delete all→upload; VP-576-003)

`jr issue attachment upload <KEY> <FILE> --replace-existing`:
1. Fetch attachment list via `GET /rest/api/3/issue/{key}?fields=attachment`.
2. Find ALL existing attachments whose filename matches the FILE basename (case-sensitive string equality; JRACLOUD-96384 — multiple attachments CAN share the same filename; all matches are deleted). Match by filename, NOT by AID.
3. If ≥1 match found: confirmation gate (BC-3.9.014 consumer 2 — see AC-007). On cancel: exit 0, no deletion, no upload.
4. Issue DELETE for each matching AID (one per AID, sequential). 404 on a delete = benign skip (stale IDs tolerated per race-window documentation).
5. After ALL deletes complete: issue the POST upload.

**VP-576-003 ordering invariant**: Wiremock test MUST assert DELETE(s) precede POST in the request log. No interleaving allowed. The test constructs a fixture with two same-named attachments and asserts: 2 × DELETE, then 1 × POST, in that order.

No matches found: proceeds directly to POST without confirmation gate (no-op replacement).

Non-atomic race window: documented in BC-3.9.017. A new same-named attachment created between step 1 and step 4 is not deleted. This is expected behavior.

- **Tests:** `tests/attachment_upload.rs::test_bc_3_9_017_replace_existing_delete_then_post`; `tests/attachment_upload.rs::test_vp_576_003_delete_before_post_ordering_invariant`

### AC-007 (traces to BC-3.9.014 postcondition: gate mechanics consumer 2; eprint! not eprintln!)

`--replace-existing` confirmation gate (BC-3.9.014 consumer 2):

Prompt (BC-3.9.014 consumer 2 verbatim — `eprint!`, NOT `eprintln!`, NOT `dialoguer::Confirm`):
