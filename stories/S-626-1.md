# S-626-1 -- Fix rust-toolchain SHA pins + MSRV false-green + comfy-table pin + CLAUDE.md gotcha

## Narrative

As a CI maintainer, I want:
1. All 6 workflow files to pin `dtolnay/rust-toolchain` to a verified master-ancestor SHA with
   an explicit `toolchain` input, so that the pin is both correct and self-documenting.
2. The MSRV job in ci.yml to actually validate Rust 1.85.0 (not stable), so that the
   minimum-supported-rust-version claim is enforced rather than silently passing on any stable version.
3. `Cargo.toml` to pin `comfy-table = "=7.2.1"` (exact, not a caret range), so that `cargo check`
   under Rust 1.85.0 is clean (`comfy-table 7.2.2` uses let-chains, which require ≥1.88.0 — see AC-8).
4. A CLAUDE.md gotcha note documenting the `rust-toolchain.toml` vs `RUSTUP_TOOLCHAIN` precedence
   resolution, so future contributors understand why the env override is necessary.
5. Three in-tree let-chain occurrences (`src/cli/board.rs:~232`, `src/cli/issue/list.rs:~524`,
   `src/cli/auth/keychain.rs`) rewritten to semantically equivalent nested `if` blocks, so that
   `jr`'s own source compiles clean under Rust 1.85.0 (see AC-9 — scope addition, v1.3).

## Problem Statement

**Defect 1 -- Stale SHA pin and wrong-version toolchain install (6 workflow files):**
All 6 workflow files currently pin `dtolnay/rust-toolchain@c93f4f9c67595668add93d3d6895795ce52d8c2d`.
This SHA is NOT a master ancestor of the dtolnay/rust-toolchain repository. It is the tip of the
action's `1.85.0` version branch (confirmed by reading the pinned `action.yml`: the `inputs:` block
declares only `targets`, `target`, and `components` — there is no `toolchain` input; the parse step
hard-codes the version `1.85.0`). The replacement `fa04a1451ff1842e2626ccb99004d0195b455a88`
was confirmed as a master ancestor at F2 (P71-001, DISCHARGED).

Two consequences of the version-branch finding (pass-3 adversary, v1.6):

1. **The SHA substitution is load-bearing, not hygiene.** On the `1.85.0` version branch the
   `toolchain` input does not exist, so adding `with: {toolchain: …}` alone would have been
   **silently ignored** (GitHub emits at most an "Unexpected input(s)" warning). The SHA swap to
   the master-branch tip is a hard prerequisite for the `toolchain:` input to take effect.

2. **Blast radius — shipped binaries were compiled by stable, not by 1.85.0.** All six jobs
   installed Rust 1.85.0 (the version branch), but `cargo build` ran under **stable** because
   `rust-toolchain.toml` outranks `rustup default` in rustup's precedence chain. Shipped binaries
   were therefore compiled by stable — NOT by 1.85.0. The concrete harm was: a wasted toolchain
   install per job, cross-compilation targets installed onto the 1.85.0 toolchain rather than the
   active stable toolchain (causing E0463 without the defensive `rustup target add` steps), and
   misleading `# stable` comments across six workflows. Do not overstate: released binaries were
   compiled by stable — the build was not broken, it was misrepresented.

**Defect 2 -- MSRV false-green (ci.yml msrv job):**
The msrv job uses `dtolnay/rust-toolchain@c93f4f9c` (the `1.85.0` version branch, which has no
`toolchain` input). The pre-fix sequence that produced the false-green:
1. The action installed Rust **1.85.0** and set it as `rustup default`.
2. `cargo check` ran in the repo root where `rust-toolchain.toml` declares `channel = "stable"`.
3. Per rustup's override precedence (`+toolchain` > `RUSTUP_TOOLCHAIN` > directory override >
   `rust-toolchain.toml` > `rustup default`), the toml outranks `rustup default`, so `cargo check`
   ran under **stable** — not 1.85.0. The false-green came entirely from this step.

Fix: swap SHA to master-branch tip (where `toolchain` input exists) AND add `with: {toolchain:
"1.85.0"}` to the action step AND add `env: {RUSTUP_TOOLCHAIN: "1.85.0"}` to the `cargo check`
step. The `RUSTUP_TOOLCHAIN` env variable outranks `rust-toolchain.toml` at the process level,
so `cargo check` runs under 1.85.0 as intended (see CLAUDE.md gotcha note).

**Emergent consequence -- comfy-table 7.2.2 MSRV violation (resolved by pin in AC-8):**
When the MSRV job was first run under the corrected 1.85.0 toolchain (story v1.1 run),
`cargo check --all-features` failed because `comfy-table 7.2.2` uses let-chains (stabilized in
Rust 1.88.0 under edition 2024). `comfy-table 7.2.2` ships no `rust-version` manifest field, so
cargo enforced no constraint when a caret range resolved to 7.2.2. This is the fix working as
intended — surfacing a genuine violation that was invisible while the job validated stable.
Resolution: pin `comfy-table = "=7.2.1"` (see AC-8). `comfy-table 7.2.1` declares
`rust-version = "1.85"` and builds clean at 1.85.0. Raising the declared MSRV to 1.88 was
attempted (v1.1) but deferred — it cascaded into 49 `collapsible_if` clippy errors across 27
`src/` files; a 27-file refactor deserves a dedicated story (S-640-1, not this story).

**Emergent consequence 2 -- In-tree let-chains (scope addition, v1.3; commit `cc7f6da5`):**
Three occurrences of let-chains in `jr`'s own source also require Rust ≥1.88.0:
`src/cli/board.rs:~232` (`&& let Some(field_id) = team_field_id`),
`src/cli/issue/list.rs:~524` (same pattern), and
`src/cli/auth/keychain.rs` (one occurrence; same construct class, mirrored operand order — `if let Ok(v) = … && !v.is_empty()`).
These were invisible while the msrv job validated stable — the false-green did not merely fail
to catch a dependency drifting past the declared floor, it let `jr`'s own source drift past it
in three places. That is the sharpest expression of what this story set out to fix. Human ruling
2026-07-30: rewrite within S-626-1 scope (see AC-9).

**Defect 3 -- Missing CLAUDE.md gotcha:**
No documentation exists explaining why `RUSTUP_TOOLCHAIN` is needed instead of relying on
`dtolnay/rust-toolchain`'s `toolchain` input alone. The gotcha must be added so future
contributors do not regress this.
