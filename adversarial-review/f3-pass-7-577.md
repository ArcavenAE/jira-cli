## Findings

### HIGH

**F-1 HIGH — `S-577-6` AC-007 exit-64 test unproducible (serde_json 128-depth limit intercepts before ADF guard fires)**
`S-577-6` AC-007 specified a subprocess Red Gate test that would trigger `adf_to_text`'s 256-depth recursion guard (BC-7.2.012), expecting exit 64. This test is unproducible: `client.rs:265` calls `serde_json::from_slice` to deserialize the API response before `adf_to_text` is ever invoked. `serde_json` enforces a hard 128-depth parse limit — a response nested deeper than 128 levels is rejected with `JrError::Json` → exit **1** (system error), not exit 64. No wiremock fixture can produce a response that reaches the `adf_to_text` depth guard on the view path because `serde_json` filters it out first. The AC as written would deadlock the Red Gate: the stub would correctly exit 1, but the AC asserted exit 64, causing an irreducible test failure with no implementation fix possible.

**Fix:** AC-007 re-specified as two-tier:
- **Tier-i (mandatory):** unit-level programmatic BUILD propagation test — call `adf_to_text` directly with a 256-deep ADF tree and assert `Err(JrError::NestingTooDeep)` propagates; this tier pins EC-3.5.010-2(a) without subprocess machinery.
- **Tier-ii (optional):** boundary exit-1 subprocess test, labeled "JSON-parse path" (tests the `serde_json` 128-depth wall, not the ADF guard) — tests that a wiremock response with 130-deep JSON exits 1.

Unreachability note added: "The `adf_to_text` 256-depth guard is unreachable on the view path in practice because `serde_json::from_slice` (client.rs:265) enforces a 128-depth limit. This is an implementation fact, not a spec contradiction — BC-7.2.012 remains correct."

### MEDIUM

**M-1 MEDIUM — `S-577-3`/`S-577-5` falsely claimed `refuse_noninteractive` internally re-derives TTY state**
Both stories cited `workflow.rs:207` as the site where `refuse_noninteractive` calls `is_terminal()` internally. Inspection of `workflow.rs:207` shows the function signature takes `stdin_is_tty: bool` as a **parameter** — it does not call `is_terminal()` internally. The `is_terminal()` call is at `handle_move`'s call site (~line 660), not inside the helper. The stories' PSI and Rule 8 sections incorrectly described the helper as self-contained, which would lead implementers to write a version that re-derives TTY state inside the helper (wrong pattern — creates a seam-defeating double-check). **Fix:** citations in PSI and Rule 8 of both S-577-3 and S-577-5 corrected to the call-site pattern (caller derives `stdin_is_tty`, passes as parameter).
