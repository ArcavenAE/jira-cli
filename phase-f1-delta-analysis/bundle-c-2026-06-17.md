## CR-001 — `list_comments` Missing Anti-Stall Guard

### Impact Boundary

**Primary file:** `src/api/jira/issues.rs::list_comments` (lines 636–674)

**Pattern:** `list_comments` loops on `OffsetPage<Comment>` with `has_more` check and
`start_at = next` advancement, but lacks the `if next <= start_at { return Err(...) }`
guard that `get_changelog` carries at lines 620–628 of the same file.

The defect class: if a pathological Jira response returns `total > current_count` (i.e.,
`has_more()` returns true) but the `OffsetPage` reports a `next_start()` equal to or less
than the current `start_at`, the loop runs forever. In practice this class is triggered by
an offset schema-drift / non-advancing-startAt scenario (empty or repeated page with stale
`has_more`), distinct from the cursor-based JRACLOUD-95368 mechanism (which applies only
to `nextPageToken`-based fetchers, not offset-based loops).

### Sibling Enumeration (LESSON-F1-SIBLING-CASE)

Full survey of every paginated fetcher in `src/api/`:

| Fetcher | File | Pagination style | Anti-stall guard | Vulnerable? | Notes |
|---------|------|-----------------|-----------------|-------------|-------|
| `search_issues` | `api/jira/issues.rs` | Cursor (`nextPageToken`) | YES — seen_keys HashSet + repeated-cursor abort (JRACLOUD-95368 class) | No | Strongest guard |
| `search_issue_keys` | `api/jira/issues.rs` | Cursor (`nextPageToken`) | YES — seen_keys HashSet + repeated-cursor abort | No | Same |
| `get_changelog` | `api/jira/issues.rs` | Offset (`startAt`) | YES — `if next <= start_at { return Err(...) }` | No | Reference implementation |
| `list_comments` | `api/jira/issues.rs` | Offset (`startAt`) | **NO** | **YES** | The defect; sibling of `get_changelog` |
| `get_issue_types_for_project` | `api/jira/issues.rs` | Offset (`startAt`) | NO — but bounded by `total` field (loop exits when `start_at + page_len >= total`) | Low risk | Total-bounded; loop converges by construction. An empty page where `page_len == 0` would still infinite-loop, but this endpoint is unlikely to return empty pages with non-zero total in practice. |
| `list_boards` | `api/jira/boards.rs` | Offset via `OffsetPage<Board>` | NO | Low risk | `has_more()` checks `isLast` field. Malformed page would loop; boards are admin-level metadata, not user content — low real-world exposure |
| `list_sprints` | `api/jira/sprints.rs` | Offset via `OffsetPage<Sprint>` | NO | Low risk | Same reasoning as boards |
| `get_sprint_issues` | `api/jira/sprints.rs` | Offset via `OffsetPage<Issue>` | NO | Low risk | Sprint content is bounded; same class |
| `list_worklogs` | `api/jira/worklogs.rs` | Offset via `OffsetPage<Worklog>` | NO | Low risk | Single-page fetch in current code (BC-X.5.002 MUST-FIX tracks the full paginator refactor); not currently a loop at all |
| `search_users_all` | `api/jira/users.rs` | Offset (fixed USER_PAGE_SIZE advance) | Implicit — advances by `USER_PAGE_SIZE` regardless of returned count (JRACLOUD-71293 documented) | Low risk | Fixed-advance means stall can't happen; loop exits when empty page returned |
| `search_assignable_users_by_project_all` | `api/jira/users.rs` | Offset (fixed USER_PAGE_SIZE advance) | Implicit (same) | Low risk | Same |
| `list_queues` | `api/jsm/queues.rs` | Offset via `ServiceDeskPage` | NO | Low risk | Admin JSM data; bounded by queue count |
| `get_queue_issues` | `api/jsm/queues.rs` | Offset via `ServiceDeskPage` | NO | Low risk | Same |
| `list_service_desks` | `api/jsm/servicedesks.rs` | Offset via `ServiceDeskPage` | NO | Low risk | Admin data |
| AQL search (`search_assets`) | `api/assets/objects.rs` | Cursor-based or page-based per Assets API | NO explicit guard found | Low risk | Assets API is structurally different; response schema has `isLast` analogue |

**Conclusion:** `list_comments` is the ONLY offset-paginated loop with real user-content
volume that lacks the guard AND has a sibling (`get_changelog`) with the pattern. The
other offset loops (boards, sprints, queues) handle metadata bounded by instance size —
real-world exposure is orders of magnitude lower. `get_issue_types_for_project` is
total-bounded so cannot infinite-loop unless `page_len` is 0 and `total > 0` simultaneously
(degenerate API behavior).

**Scope decision:** Fix `list_comments` only. Do NOT add guards to boards/sprints/queues
loops in this bundle — they are low-risk, have no reported stalls, and changing them is
out of scope for a targeted maintenance sweep. Document the finding here as `DEFERRED-LOW`.

### Affected BCs / NFRs

- **BC-2.4.039** — `issue comments <key>` paginates at 100/page. The AC covers
  normal pagination; the guard is a NEW sub-contract: "stall-proof even if server
  returns has_more=true without advancing startAt." **NEW AC required** under BC-2.4.039
  or as BC-2.4.043 (new BC for stall-guard).
- **BC-2.4.042** — `list_comments(key, None)` lists ALL comments. Guard is a
  reliability qualifier on this BC.
- No NFR directly covers the guard; it is consistent with the project's existing defensive
  pagination pattern established in `get_changelog`.

### Test Impact

Existing `tests/comments.rs` covers: basic pagination, empty, limit, paginated (4 tests).
No test covers the stall-guard path. A new test is required:
`test_list_comments_stall_guard_returns_error_when_start_at_does_not_advance`.
The test uses wiremock to return `has_more=true` with a page that doesn't advance `startAt`.

### Regression Risk: LOW

Single-function change, 3 lines maximum. `list_comments` has 4 existing tests that
serve as regression baseline. No other code path changes.

### Change Pattern

Match `get_changelog` exactly:
```
if next <= start_at {
    return Err(anyhow::anyhow!(
        "Jira comment pagination did not advance (startAt {} → {}) ...",
        start_at, next
    ));
}
start_at = next;
```

## CR-002 — JSON-Render Inconsistency (24 direct `to_string_pretty` sites)

### Impact Boundary

**Affected files:**
- `src/cli/issue/create.rs` — 6 sites (lines 263, 279, 758, 1100, 1262, 1486)
- `src/cli/issue/workflow.rs` — 7 sites (lines 294, 419, 931, 1037, 1052, 1082, 1106, 1172)
- `src/cli/issue/links.rs` — 4 sites (lines 99, 197, 216, 278)
- `src/cli/auth/login.rs` — 1 site (line 334)
- `src/cli/auth/logout.rs` — 1 site (line 43)
- `src/cli/auth/switch.rs` — 1 site (line 44)
- `src/cli/auth/remove.rs` — 1 site (line 122)
- `src/cli/auth/list.rs` — 1 site (line 51)
- `src/cli/auth/refresh.rs` — 1 site (line 141)

Total: 24 non-test sites.

**NOT affected:** `src/cli/sprint.rs` already uses `output::render_json` at 3 sites.

### Behavior-Preserving Assessment

`output::render_json<T: Serialize>(data: &T) -> anyhow::Result<String>` is:
```rust
pub fn render_json<T: Serialize>(data: &T) -> anyhow::Result<String> {
    Ok(serde_json::to_string_pretty(data)?)
}
```

The only behavioral difference is error-type wrapping: `serde_json::to_string_pretty`
returns `serde_json::Error`; `render_json` converts it to `anyhow::Error`. At all 24
call sites, the result is either `?`-propagated (same behavior after conversion) or
directly `.unwrap()`/`?`-used inside `println!`. **The change is behavior-preserving
at all 24 sites.** No formatting, newline, or content difference exists.

### Load-Bearing Sites Check

Sites where the difference COULD matter (not applicable here, but checked):

- `workflow.rs:931` — `println!("{}", serde_json::to_string_pretty(&payload)?)` — a
  `--dry-run` path. `render_json` is identical; safe.
- `create.rs:758` — another dry-run path. Safe.
- `auth/list.rs:51` — returns `Ok(serde_json::to_string_pretty(&arr)?)` directly from
  a function returning `anyhow::Result<String>`. The `?` auto-converts from
  `serde_json::Error` to `anyhow::Error` — `render_json` does the same explicitly. Safe.

**Conclusion:** All 24 sites are safe to replace. Zero behavioral difference.

### Affected BCs / NFRs

- No BCs are changed. This is a pure mechanical refactor of the implementation path,
  not a behavioral change. All existing JSON output BCs (BC-3.*, BC-2.*, auth BCs)
  continue to hold unchanged.
- NFR-O (output channel discipline): refactor improves centralization; enables future
  global JSON transforms (syntax highlighting, `_meta` envelope, NFR-O-P). No NFR
  target changes.
- **No new BCs required.**

### Test Impact

No test changes required. The output bytes are identical.
Existing snapshot tests (if any) will pass without change.

### Regression Risk: VERY LOW

Mechanical find-and-replace. Output bytes identical. Error type conversion is already
happening via `?` at all sites (anyhow auto-converts from serde_json::Error).

## CR-007 — `write_object_type_attr_cache` Silent Error Discard Undocumented

### Impact Boundary

**Primary file:** `src/api/assets/objects.rs` line 189

**The situation:**
- `write_object_type_attr_cache` in `src/cache.rs` is a **propagate model (a)** writer:
  its body uses `?` on all fallible operations and returns `Result<()>`. It does NOT
  swallow errors internally.
- Its only production call site in `objects.rs:189` uses `let _ = cache::write_object_type_attr_cache(...)`,
  silently discarding any error.
- The call site has a `// Best-effort cache write` comment, indicating the intent is
  model (b) / swallow+warn, but the implementation is model (a).
- CLAUDE.md documents the two-model policy and requires rustdoc on the writer choosing
  the model. `write_object_type_attr_cache` has no such rustdoc.

**Secondary related finding (scope note):**
`src/api/assets/linked.rs:34` uses `let _ = cache::write_cmdb_fields_cache(profile, &fields)`
which is the same pattern — but `write_cmdb_fields_cache` is a propagate model (a) writer
with NO swallow+warn documentation and NO `eprintln!` internally. Its call site also
silently discards. This is a pre-existing analogous issue that should be fixed in the
same PR for consistency, but was not flagged in the original sweep finding.

### Correct Disposition

The call-site intent is clearly model (b) (best-effort, non-critical acceleration cache).
The canonical fix is to align the WRITER to its call-site intent: convert
`write_object_type_attr_cache` to a best-effort writer matching `write_fields_cache`:

```rust
/// Best-effort writer: swallows disk-write errors with `eprintln!` and returns
/// `Ok(())`. A missed write costs at most one extra HTTP fetch on the next
/// invocation. Cache write failures MUST NOT break a successful API call.
///
/// Chosen model: (b) swallow + warn — this cache is a read-acceleration
/// shortcut for CMDB object-type attribute lookups, not a correctness-critical store.
pub fn write_object_type_attr_cache(...) -> Result<()> {
    let result = write_cache(...);
    if let Err(e) = result {
        eprintln!("warning: failed to write object_type_attrs cache: {e}");
    }
    Ok(())
}
```

Then remove the `let _ =` at the call site (replace with `cache::write_object_type_attr_cache(...)?`
which now always returns `Ok(())`). Same outcome as before, but self-documenting and
consistent with the policy.

Apply the same fix to `write_cmdb_fields_cache` — change the writer to model (b) and
update the call site in `linked.rs`.

Add a CLAUDE.md gotcha note for `write_object_type_attr_cache` mirroring the existing
request-type cache entry.

### Affected BCs / NFRs

- No BCs are changed. Cache-write behavior is not part of any behavioral contract.
- CLAUDE.md Gotchas section: add new entry documenting `write_object_type_attr_cache`
  and `write_cmdb_fields_cache` as model (b) writers.
- **No new BCs required.**

### Test Impact

The existing `tests/cache.rs` tests for `write_object_type_attr_cache` (lines 1032, 1095–1096)
call the function with `.unwrap()` — they will continue to pass since the writer now always
returns `Ok(())`. A new test should verify the swallow behavior:
`test_write_object_type_attr_cache_swallow_io_error_returns_ok` (mirrors existing
`test_write_fields_cache_swallow_io_error_returns_ok` at line 963).

Same for `write_cmdb_fields_cache`: new test
`test_write_cmdb_fields_cache_swallow_io_error_returns_ok`.

### Regression Risk: LOW

The external behavior at the `objects.rs` call site is unchanged — the error was already
being discarded. The change is that we now emit a `warning:` to stderr on failure (net
improvement for observability) and the writer's signature is self-documenting.

## Story Split Recommendation

### Option A: One story (Bundle C as single PR)

All three items are in `src/api/jira/issues.rs` + `src/cache.rs` + mechanical CLI refactor.
They can logically coexist in one PR with limited cross-file blast radius.

**Pros:** One review cycle, one merge, atomically clean.

**Cons:** CR-002 touches 10 CLI files across multiple subsystems (create, workflow, links, auth, sprint).
A reviewer would have to mentally separate the anti-stall guard logic from the mechanical refactor.
The diff would be large (50+ lines changed across 10+ files).

### Option B: Two stories/PRs (recommended)

**PR 1 — Pagination guard + cache-write alignment (CR-001 + CR-007)**
- Files: `src/api/jira/issues.rs`, `src/cache.rs`, `src/api/assets/objects.rs`,
  `src/api/assets/linked.rs`, `tests/comments.rs`, `CLAUDE.md`
- Rationale: Both are correctness/reliability fixes in the API and cache layers.
  Related ownership (API/cache concern), reviewable together.
- Story label: `fix/pagination-guard-cache-write-alignment`

**PR 2 — JSON render unification (CR-002)**
- Files: `src/cli/issue/create.rs`, `src/cli/issue/workflow.rs`, `src/cli/issue/links.rs`,
  `src/cli/auth/{login,logout,switch,remove,list,refresh}.rs`
- Rationale: Pure mechanical refactor, zero logic changes, large cross-file diff.
  Separate review makes the "all identical substitutions" claim easily verifiable.
- Story label: `chore/unify-json-render`

### Severity/Priority Order

1. **CR-001** (pagination guard) — address first; has a new-test requirement and touches
   correctness of a documented anti-pattern class. LOW severity but the only one with
   a theoretical infinite-loop risk.
2. **CR-007** (cache-write alignment) — address in same PR as CR-001; 1–3 lines of
   implementation change + rustdoc. Zero risk.
3. **CR-002** (JSON render unification) — address in separate PR; pure mechanical,
   zero risk, but widest file footprint.
