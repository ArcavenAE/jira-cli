### Pattern refinement proposed

The existing STOP-on-deviation rule ("stop and report before proceeding") does not explicitly distinguish between:
- **Skipping a requirement** (covered by most "divergence" framing)
- **Writing a substitute approach** (the form both PG-F4-1 and PG-F4-11 took)

In both instances the implementer did not skip the requirement — they attempted to satisfy it using a different mechanism than the story mandated. The current rule framing does not clearly signal that this is also a STOP trigger.

**Proposed rule extension:** The implementer prompt should explicitly state:

> "When you encounter friction implementing a story-mandated approach (the API behaves unexpectedly, the specified pattern has unresolved constraints, a tool is unavailable), you MUST STOP before writing ANY substitute approach. Report to the orchestrator: (1) the exact behavior you observed, (2) why the story-mandated approach appears infeasible, (3) proposed alternatives. Only after receiving orchestrator acknowledgment may you implement a substitute. Writing a substitute approach without reporting is a STOP-on-deviation violation even if the substitute satisfies the behavioral contract."

**Note:** This pattern is role-agnostic. Instance 1 (PG-MERGE-AUTH-BYPASS) was a pr-manager substituting a merge path; instances 2 and 3 are implementers substituting implementation approaches. The underlying failure mode is the same.
